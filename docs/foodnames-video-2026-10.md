## 一、先把「明显的问题」变成能机检的数字

用户说的「有明显的问题」原本是观感。观感不能当验收口径，所以第一步是把它拆成 **五条可机检的缺陷**，每条配一道能跑的判据。

| 编号 | 缺陷 | 判据怎么量 | 旧 12 期实测 |
|---|---|---|---|
| **D1** | **画面上的句子不是配音念的那一句**（最重） | `check_sentence_matches.mjs`：跑真实构建器抽画面可见文字，与数据里的旁白句去空白去标点后逐词比 | **54/144 个语种-期组合不一致**（37%） |
| **D2** | 视频里没有「菜名」这个主角（词只是句首的一个 token，词形墨迹只占画面高 4.5%–13.3%） | `check_video_layout.mjs`：DOM 探针量词形盒子的实际占比 | 12 期全中 |
| **D3** | 竖屏最大空白带 26%–30% | 同上，像素层扫最大空带 | 12 期全中 |
| **D4** | 未唱到的 token 不透明度 0.18（几乎隐形） | 同上，量实际不透明度 | 12 期全中 |
| **D5** | 当前词高亮是中性灰 `rgba(44,38,32,.09)`，不在页脚图例承诺的三色里 | 同上，量实际高亮色 | 12 期全中 |
| ~~D6~~ | ~~注音对位偏移~~ | —— | **实测 0.0–1.4px，不是缺陷，被量尺子否掉** |

D1 的现场（法语第 01 期，画面 vs 配音）：

```
fr-FR  画面 "sushi sushi est un plat japonais"   配音 "Le sushi est un plat japonais"
ja-JP  画面 "茶ちゃ は 中国 から 来た"              配音 "茶は中国から来た"
```

根因在 `usine/tools/foodnames/build_episode.mjs`：为了给菜名上色，它把句子的 **第一个 token 无条件替换成词形**。句首不是那个词的语种——冠词（Le / El / Το）、日语助词「は」、韩语助词「는」——那个 token 被吃掉，词本身若在句中再现就重复一遍。后果是**音画不同步**：卡拉OK 按 token 逐个亮，token 数没变但内容整体错开一词。

`verify-sync` 门抓不到它——那个门只数词数，不比词。

**旧 12 期的完整基线**：版式门合计 **954 条不达标**（每期 76–83 条），句子门 **54 处**。

## 三之二、合并带进来的下游回归：韩语补丁（工作区主人抓到的）

波次落地后跑完整产线，第 12 步 `poster audit-charset` **六期全红**：

```
PATCH-RULE BINDING PROBLEMS:
  orphan rule .kC2A4 is defined but worn by no glyph
```

**病因**：波次把韩语在视频侧改成了 `.cv` 融合渐变，理由写在代码注释里——「补丁类 `.k####` 的 background-position 是按**海报**字号实测的；视频的主角词被拟合到另一个字号，补丁必然错位 → 视频一律走 `.cv`」。

**这个前提是错的。** 补丁用的是**百分比**定位：

```css
.kC2A4 { background-position: 0.0% 100.0%, 0 0; background-size: 100.0% 38.7%, 100% 100%; }
```

而测量页自己写着「（advance × line-height），**任意 font-size 可迁移**」（`packages/poster/src/measure_korean.ts`）。所以「字号变了补丁就错位」不成立。

**代价有两处，都很实**：

1. 注入 `video_src.html` 的 `.k####` 规则变成「无人穿戴的孤儿规则」，`poster audit-charset` 当场红，**整条产线在第 12 步停住**——12 期一期都出不来；
2. 韩语丢掉页脚图例承诺的**元音/辅音分色**（整词只剩一条对角渐变），与图例自相矛盾。

**修法**：视频侧继续用实测补丁，`.cv` 只留给数据里显式声明的**融合音节**（`ko_fused_syllables`，那才是没有补丁可用的场合）。另外把 `.ksyl` 的 `line-height` 留回 **1.28**——补丁量在「advance × 1.28 行高」的盒子上，行高一改墨迹在盒里的相对位置就变（字号变了没关系，百分比会跟着缩放）。

**这一条是本轮最值钱的方法论**：合并门禁管不到 `tools/`（`vitest.config.ts` 的 include 只有 `packages/*/test/**/*.test.ts`），所以「波次说它修好了」和「产线还能跑」是两件事。**只有把整条产线真跑一遍，才知道合并带进来了什么。**

## 三之三、guest 里那道结构门是**环境性红**（量到的不是缺陷）

波次日志里 Actor 反复撞同一道门：`packages/gate/test/layout.test.ts` 报

```
仓库根多了 ["AppData","bin","evolution_project","work"]
```

查下来：guest 的 seed 是「把 **usine 前缀**的 git-archive 解到 `/home/user`」，于是 `packages/gate/test/layout.test.ts` 算出来的「仓库根」= `/home/user` = **HOME**，里面那四个目录是 **harness 自己的**（`bin` / `work` 是建机时的，`AppData` 是 Windows 版 Node 跑 vitest 时自己长出来的）。

也就是说：这道门在 guest 里**量错了目录**——它把 harness 的家当当成了「内容产物」。真仓库里它是绿的（仓库根只有 `usine/ garage/ garage-ii/ theatre-ii/ théâtre/ config/ docs/`）。

**代价**：Actor 拿它当自己的验收信号，绕着它耗掉十几次迭代；验证席也因为 `AppData` 还在，连着 5 轮跑同一条命令（重复确认不是新证据）。

**处置**：本轮不动这道门——它是「人手工维护的白名单」，动它的收益（省几轮迭代）远小于风险（把一条故意的门改成"对 guest 放行"）。记在这里，作为后续单独一件事。

## 三之四、量「之后」时发现：**尺子自己有缺陷**（隔行采样漏掉细线）

第一轮「之后」测完：版式门 **13 条不达标**，全部是 `no_big_empty_band`，全部在 15.4%–15.6%（阈值 ≤15%）。差 0.4–0.6 个百分点。

按纪律先查「这是我引入的，还是尺子的」——逐帧定位那条空带的位置：

```
ep05-chocolate / de-DE / 竖屏：
  隔行采样（现在的口径）= 15.5%（297px，位于 y=1541..1838）
  逐行扫描                =  9.7%
```

**根因**：页脚那条 1.5px 的分隔线渲染在 **y=1687（奇数行）**，而像素扫描是 `for (y = 0; y < H; y += 2)`——**只取偶数行**。于是那条细线整条没被看见，「细线上面 ~146px + 细线下面 ~149px」两段空气被并成一段 297px。

原注释写的是「行按 2 抽样（空白带是连续行，2 倍抽样最多差 1 行误差）」——**这句话是错的**：误差不是 1 行，是**整条细线加它两侧的空气**，量级 ~150px。更糟的是这个假阳性会**随细线落在奇数行还是偶数行而翻转**：同一份版式，量出 297px 或 150px 都可能。

**修法**：像素层改成**逐行扫**（`y += 1`）。代价是每帧多扫一半的行（实测多 ~0.3s）。

**代价与纪律**：尺子换了，**两侧读数都得重测**——「之前」的 12 期（旧成片的帧还在盘上）与「之后」的 12 期都用新尺子各跑一遍，报告里写明旧读数作废的理由。

**顺带否掉一条**：判据自己也写着「D6 注音对位偏移」早就被量尺子否掉了（0.0–1.4px）。连判据自己都会量错，这轮又量出来一次。

## 三之五、渲染环境翻转把整条产线打断：**视口亏空**（Edge 144 的 headless 窗口比视口高 93px）

第二轮「之后」重新生成 12 期，**12 期全部在第 14 步失败**（`poster verify-colors` 报 `grid not found`）。同一个提交、同一台机器、昨天还跑得通——所以先查「是不是我改的」。

把「网格没找到」拆开量，链条是这样的：

1. `verify-colors` 只找到 **4 条横线**（要 5 条：4 行格子 = 上下 5 条边），竖线 4 条全对；
2. DOM 探针量到网格底边**几何上完全正确**（`.grid` 底边 1713px，画布 1754px）；
3. 于是问题不在版式，在**出图**：新海报的左列在 **y=3322（=1661 CSS px）**处从纸色（247,242,230）变成底色（232,226,212）——**画布底部 93px 根本没被画上**。

根因是 Chromium 系的一个坑：`--window-size=W,H` 给的是**窗口**尺寸，实际**视口**更矮。本机实测（两种浏览器各量一次，**四种窗口尺寸的亏空都一样**）：

| 浏览器 | 版本 | 请求的窗口 | 实际视口 | 亏空 |
|---|---|---|---|---|
| **Edge（产线实际用的）** | 144.0.3719.82 | 1240×1754 | 1216×1661 | 宽度 24 / **高度 93** |
| Chrome（产线没用到） | 155.0.8059.85 | 1240×1754 | 1224×1659 | 宽度 16 / 高度 95 |

**产线用的到底是哪一个**：`platform.browserPath()` 实测输出 `edge: C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`——候选表里 edge 排在 chrome 前面，`FEUILLE_BROWSER` 为空。**Chrome 155 确实是 10-20 08:23 自动升级的，但产线压根没用到它**（Edge 自 2026-01-20 装上 144.0.3719.82 之后没动过）。第一版归因写的是「Chrome 自动升级」，被这条实测推翻了。

**破口不是内容回归，也跟浏览器升级无关**——两条决定性实验：

1. **旧内容今天也坏**：拿 10-20 01:10 交付的那份 `index.html`（`foodnames-ep01-sushi/index.html`），用今天的 Edge、同一套参数、不带补偿重渲 → **底边同样被切**（y=3322 起是底色，网格底线 3425–3427 消失）。所以「换了新模板才坏」不成立。
2. **同一份 HTML、同一枚二进制，10-20 渲得完整、今天渲不全**：旧交付的 `poster.png`底边是好的（`run.log` 里 `horizontal lines: [490, 1224, 1958, 2692, 3426]`，第 5 条在 1713 CSS px），而 Edge 二进制自 1 月起没换过、渲染参数也没换过——**翻转发生在渲染环境侧**（旧 12 期渲于 10-20 01:10–02:29，失败的重新生成在 10-21 21:06 之后），具体是显示/桌面会话/DPI 布局里的哪一项翻转了，**没定位到**。

**为什么 10-20 那天没出事**：仓库里早就有这个坑的补丁——`packages/core/src/textlayer.ts`（视频帧走它）会**先探一次亏空再补窗口**；`packages/poster/src/render_page.ts`（Windows 专用的整页渲染器）也有一份，但**写死了常数 (24, 93)**——今天实测 Edge 144 恰好就是 (24, 93)，说明那个常数本来就是给这台机器的 Edge 探的。

**而产线真正走的那条路没有补丁**：`packages/poster/src/render_poster.ts`（CLI 的 `poster render`）**原样把 `w,h` 塞进 `--window-size`**。于是：

- 海报（1240×1754，2x）：底部 93 CSS px 被切 → 网格底边正好落在那儿 → `grid not found`；
- 封面（1080×1920，1x）：底部 166px 被切；
- 视频帧（走 textlayer）：**没事**——那条路早有补偿（实测帧的左右两列到底都是纸色）。

**修法（不写死常数）**：`packages/core/src/platform.ts` 新增 `viewportDeficit(browser)`：渲一页只报 `innerHeight` / `clientWidth` 的探针页，量出差值，按浏览器路径 memoize；三个渲染口（`render_poster` / `render_page` / `measure_korean`）都改成**按实测亏空补窗口高度**，渲完把 PNG 裁回 `w*scale × h*scale`。

两条细节是实测逼出来的：

- **只补高度**。宽度也补的话，`--hide-scrollbars` 让排版宽度等于窗口宽，居中内容会被整体推开——海报网格的竖线从 `[101, 860, 1619, 2378]` 挪到 `[117, 876, 1635, 2394]`。
- **韩语测量页也得补**：三音节词（例：초콜릿）的第三个音节正好落在被切掉的区间里，墨迹掩膜被切 → 量出来的连通域是残的。

**修复的还原性（最硬的一条证据）**：用修好的渲染口重渲**旧期**的 `index.html`，得到的 PNG 与 10-20 交付的 `poster.png` **逐像素 AE = 0**（2480×3508 全部相同）。也就是说这个修复不是「画得更好看」，是**把 10-20 的行为精确还原**，而且不再依赖「那天的环境是不是这样」。

**这一条属于「量到的缺陷」还是「环境」**：环境翻了（渲染环境的某一项状态变了），但**产线该扛住**——写死的常数迟早过期，过期那天不报错，只让画面「看起来矮了一点」。

## 三之六、D1 的合并门禁：而且它**不是恒过的探针**（反向验证）

合并门禁管不到 `tools/`（`vitest.config.ts` 的 include 只有 `packages/*/test/**/*.test.ts`），所以 D1（画面句子 != 配音句）**不会被任何现有门禁抓住**——这正是它当初能进仓库的原因。补法是 `usine/tools/foodnames/test/sentence_gate.test.ts`：它**不重实现一遍判定逻辑**（重实现的断言只能证明「我重写的那份逻辑自洽」），而是直接跑**真实构建器 + 真实离线门**（`check_sentence_matches.mjs --data …`），挑三期各带一类不同的坑（ep01 的冠词形态 / ep04 的韩语融合音节 / ep06 的「카레는」词缀在 token 内部）。

但**恒过的探针等于没有探针**——所以这条门必须反向验证过。2026-10-22 实测：把 D1 的修法**撤掉**（`sentenceHtml()` 里把 token 序列改回「无条件把第一个 token 换成词形」，同时把构建期自检的基准也换成同一份序列，好让缺陷真的走到 HTML 里、由离线门来抓），离线门**当场红**：

```
（exit 1；同一批数据在修好时 exit 0）
```

还原后文件逐字节回到 HEAD，门重新变绿。**这一条是这道门能进合并门禁的前提**：一道从没红过的门，跟没有门是一回事。

## 三之七、发布侧补齐：**内容可以带过来，规格必须重取**

新 12 期跑完后发现 `publish/` 是空的——产线的发布侧以「作者写好的发布词」为输入，没有 `publish/xiaohongshu.md` 就**跳过**（脚本自己写明「不是失败」）。旧 12 期有三份，`usine/tools/foodnames/README.md` 也把「三平台发布词」列为一期的组成部分，所以这一批**缺了这一格就是交付不完整**。

先问「能不能直接搬」。答案是**能，但有三件事必须逐项核过**：

| 搬什么 | 能不能搬 | 凭什么 |
|---|---|---|
| 语言学内容（这道菜的来路、12 格谁借谁、每格位次） | **能** | A 线波次只改了 `build_episode.mjs` 与两份模板，**数据文件一个字没动**（`git show --stat 6985542` 只有那 3 个文件）→ 12 期的结构量（语种数、来路数、各「借自 X」的格数、每格位次）**逐项核对一致** |
| 规格数字（时长、帧数、电平、gain） | **不能** | 成片重渲过，规格全变——但读者面正文里根本没有这些数，`facts.json` 由 `make_publish.mjs` 从**新成片**实测生成（ffprobe + 旁白实测 + 床边车），规格自动跟着新交付物走 |
| 描述画面的句子 | **不能** | 旧 B 站简介有一句「视频里它们各自站在句子里」——那描述的是**旧版画面**（词形只是句首的一个 token，正是 D2 那个缺陷）。新版词形是**独立主角**，这句必须改。按 skill 的「不解释画面」，改法是**删掉画面那半句、留下语言学那半句**（「英语和俄语的首字母大写，是句首的正字法，不是另一个词形。」），**不是**改写成另一句画面描述 |

所以做法是：**搬 36 份原稿 + 改 2 句 + 重算 12 期事实表**，然后过两道门：`feuille copy check <publish> --facts facts.json`（8 条机检：标题字数 / 尾随空格 / 互动钩 / 置顶话术 / no-hard-wrap / AI 指纹 / 必需段落 / **数字溯源**）与 `feuille publish check-plan <manifest> --root <期目录>`（素材在盘 / 标题合规 / 横竖配对）。**12 期全绿，零失败**（每期 `publish/` 8 个文件：三份平台原稿 + `facts.json` + 三份 `copy-*.md` + `manifest.json`）。

顺带一条纪律：**「作者手写的内容」不等于「不能自动化」**。这次的自动化边界很清楚——**内容不重写（因为数据没变）、规格不抄（因为要重测）、画面描述逐句核**。判据是「这句话说的是**交付物**还是**内容**」：说交付物的要重取，说内容的才可带；说画面的**一句都不能照搬**。
## 四、B 线（harness2 × garage-ii）：它能改什么、改不到什么

### 4.1 这一格量的是什么

`garage-ii/bench_usine.py` 加了 `foodnames-scene` 一格，判据是两条**结构无关**的静态事实（不认 class 名、不认 DOM 形状）：

1. 有没有一个元素的可见文字**恰好等于**那句旁白；
2. 词形有没有**独立于**那句话成元素（「词只是句首的一个 token」不算）。

夹具直接读产线的数据文件（`tools/foodnames/data/ep01-sushi.json`），不另抄一份——抄一份就会漂，漂了的夹具会让「判据失败」变成「夹具过期」。

这一格量的是**harness 有没有把这条产线的 house rule 教给智能体**：基准 harness 的 `skills/` 里没有 foodnames 手册，所以智能体不知道「词是主角」「旁白句不许被改写」。

### 4.2 B 线改不到已交付的成片（这一条必须讲清）

harness2 演化的是 **harness 树**（systemprompt / guardrails / skills），也就是「智能体现场怎么搭一个场景」。而已交付的 12 期成片是 **`build_episode.mjs` 跑出来的代码产物**——B 线的杠杆够不着它。

所以两条线的分工是：

- **A 线改记忆 + 改仓库代码** → 能直接改掉已交付成片的生成方式；
- **B 线改 harness** → 改的是「智能体现场搭出来的场景 HTML」，要落到已交付成片上，还得有人把 harness 里的版式知识搬进 `build_episode.mjs` / `templates/video_style.css`。

这不是「B 线没用」，是**两条线的杠杆不一样**，报告里不许含糊。

### 4.3 B 线的实测读数（基准臂零分布）

要谈「演化有没有用」，先得有**同树零分布**——同一棵 harness 树、同一道题、同一个模型，重复 rollout 的分数会在一个宽度里动。没有零分布，「提升」这个说法就没有依据。

第一版基准臂（timeout 900s）**四条 rollout 全部被时钟砍掉**，零分布被污染，那一臂作废。重跑（timeout 1800s，tag `fn-base-t1800`，n=4）才作准：

| 分数 | `[0.3333, 1, 1, 0]` |

| 极差 | **1.0**（从 0 到 1 满铺） |
| 标准差 | 0.5 |

### 4.4 sweep 跑完了，但**一棵演化树都没产出**（三个原因叠在一起）

`--phase sweep --split train --seed 7 --k 1 --only-domains foodnames --timeout 1800` 跑了 `base1` / `dom1` / `inv1` / `agg1` 四条 rollout，产物都在盘上，但**演化这一步是空的**：

### 4.5 那就自己写一棵演化树，把 B 线的杠杆单独量一遍

**这个「演化」是谁做的，必须说清楚**：树是**我手写的**，不是 harness2 的提议者产出的。所以这一格量的是「**harness 树里多一条针对这条产线的手册，能不能把这一格从 0.58 拉上去**」，**不是**「harness2 自演化有没有用」。后者这一轮没有证据——sweep 没交出树（§4.4）。

树放在仓库外：`D:\coding\personal\garage-ii-result\trees\fn-evo-s1\foodnames-scene\`。逐文件核对过（不是「凭印象」）：与基准树（`garage-ii/harness_base`，15 个文件）相比，**15 个共有文件折叠 CRLF 后逐字相同**（只差行尾）；演化树**多出 3 个文件**——`skills/foodnames-scene/SKILL.md`（3281 字节，那份手册），以及引擎写回时带出来的 `skills/README.md` / `scripts/README.md`（两个都只有一行 HTML 注释，讲「加一个 skill 要怎么写」，**不带任何可见内容**）。**唯一的实质差异就是那一份手册。**

### 4.6 手写演化树的读数：三轮读数 + 一个**查出来的真缺陷**

跑法（repeat 不需要 ack，compare 也不需要）：

```powershell

# 演化臂（树 = 基准树 + 手写的 foodnames 手册）
python garage-ii\run_usine_h2.py --phase repeat --root D:\coding\personal\garage-ii-result `
  --tree D:\coding\personal\garage-ii-result\trees\fn-evo-s1 `
  --repeats 4 --tag fn-evo-s1 --only-tasks foodnames-scene --arm-workers 4 --timeout 1800
# 读数
python garage-ii\run_usine_h2.py --phase compare --base-arm fn-base-t1800 --evolved-arm fn-evo-s1 `
  --root D:\coding\personal\garage-ii-result
```

两臂用的是**同一道题、同一道判据、同一个模型、同一个上限**（上限变了旧读数就作废），唯一的差别是树：基准树 vs 基准树 + 手写的 foodnames 手册。两臂的树签名不同（`d50a6a043d260dc4` vs `05d42c12679bdf33`），所以这一格**不是**「演化没动」的零格。**第三轮多了一个变量**：工具面（那是本轮修掉的缺陷，见下），所以第三轮的臂名带 `f` 后缀。

#### 第一轮：上限 1800s——量到的是「谁先跑完」

| 臂 | 4 次 rollout 的分数 | 均值 |
|---|---|---|
| 基准臂 `fn-base-t1800` | 0.3333 / **1.0** / **1.0** / 0.0 | 0.5833 |
| 演化臂 `fn-evo-s1` | 0.0 / 0.3333 / 0.0 / 0.0 | 0.0833 |

`compare` 的判决：**Δ = −50.0，p = 0.99，演化臂「更差」**；它自己的汇总行写的是「1/1 格**有演化但分不开**（不显著或方向不对）——**不能**据此说演化带来了提升」。

但查退出码发现：**演化臂 4 条 rollout 全部 `exit 124`（被上限掐死）**，事件流全停在一条没有结果的 `tool/call`（`usine_poster fit-diag`）上。**这一格比的不是「场景搭得好不好」，而是「在上限内有没有跑完」。**

#### 第二轮：上限翻到 3600s，两臂同跑——上限不是唯一原因

（锁的粒度是**臂名**，不同臂各写各的目录，可以并行；两臂同跑＝同一台机器、同一时段，环境更公平。）

| 臂 | 4 次 rollout 的分数 | 均值 |
|---|---|---|
| 基准臂 `fn-base-t3600` | 0.3333 / 0.3333 / 0.0 / **1.0** | 0.4167 |
| 演化臂 `fn-evo-s1-t3600` | 0.0 / **1.0** / 0.3333 / 0.0 | 0.3333 |

判决：**Δ = −8.33，p = 0.76**——仍然读不出提升，但幅度从 −50 收到 −8.3。**逐条失分率更能说明问题**：两条「场景质量」判据（画面句子对得上配音句、词形独立成元素）**两臂一模一样，都是 75% 失分**；只有「交没交出场景文件」从 25% 变成 50%。而两个满分（1.0）**一个在基准臂、一个在演化臂**——**能不能拿到满分与手册无关**。

#### 插曲：查「为什么一半 rollout 交不出东西」——**真缺陷，不是智能体的问题**

普查口径：每条 rollout 的**最后一个事件 + 退出码**（`exit 124` = 被上限掐死）；「未回结果」= 有 `tool/call` 没有对应的 `tool/result`。

| 轮次 | 卡在工具调用里的条数 | 卡在哪个工具 |
|---|---|---|
| 1800s 基准臂 | 2 / 4 | `usine_karaoke build`、`usine_poster fit-diag` |
| 1800s 演化臂 | **4 / 4** | 全部是 `usine_poster fit-diag` |
| 3600s 演化臂 | 3 / 4 | 全部是 `usine_poster fit-diag` |

**两轮 16 条 rollout 里 9 条卡在工具调用，其中 8 条卡在同一个调用上。** 根因：`poster fit-diag` 缺参数时去读 **stdin**（`argv[0] === undefined ? … : readFileSync(0)`），而工具面里叶子是**同进程**跑的（`dsh-plugin` 的 `runMain` 直接 `await fn(argv)`），stdin 是**宿主自己那根永远不关的管道** → `readFileSync(0)` **永久阻塞**。

**所以「演化臂更差」的真实机制不是「手册让智能体变笨」**：手册里写着「渲染走工具面（fetch-fonts → assemble → render → audit-charset → verify-colors）」，智能体照做就踩到这颗地雷——**演化臂 4/4 全踩，基准臂只有 1/4 踩**。这是**工具面的缺陷**，按纪律「量到的到底是智能体还是我自己的环境/上限」，这一格**不能**写成「加手册让智能体变差」。

**修法（掐在边界，不改被测行为）**：`dsh-plugin` 的 `install()` 设 `FEUILLE_STDIN=off`（工具面里没有可用的 stdin）；`poster fit-diag` 缺参数或文件不存在 → **立刻 exit 2 + 用法错**，不再读 stdin（管道用法 `-` 显式保留，**CLI 那条路一个字没改**）；`poetry audio-profile` 的 `readStdin()` 同款。回归钉子两处：叶子级（`packages/poster/test/fit_diag.test.ts`：空参 → 2、文件不存在 → 2、给了文件 → 0）与工具面级（`packages/dsh-plugin/test/plugin.test.ts` 吃构建产物、走真工具面调一次 `usine_poster fit-diag` 空参，断言**立刻** exit 2 而不是挂死）。

**修完在真跑批里当场见效**：同一批 `fit-diag` 调用，修复前每条 rollout 都留下一次「未回结果」，修复后**全部当场回结果**（第三轮的完整普查：8 条 rollout、21 次调用、**未回 0**）。

#### 第三轮：工具面修好后重跑（唯一变量 = 工具面）——**地雷才是前两轮的主因**

两臂都在 3600s 上限下重跑，**唯一变的是工具面**：同一道题、同一道判据、同一个模型、同一个上限、同一台机器同一时段（锁的粒度是臂名，两臂并行）。修好之后**没有一条 rollout 停在工具调用上**——8 条 rollout 里的 **21 次** `fit-diag` 调用**全部当场回结果**（未回 0）；末事件里 6 条是 `turn/end`，另 2 条（演化臂 r3/r4）是被上限掐死、停在 `step/start`，**没有一条停在工具上**。

| 臂 | 4 次 rollout 的分数 | 均值 | 零分布宽度 |
|---|---|---|---|
| 基准臂 `fn-base-t3600f` | **1 / 1 / 1 / 1** | **1.0** | spread 0、stdev 0 |
| 演化臂 `fn-evo-s1-t3600f` | 1 / 1 / **0.3333** / 1 | 0.8333 | spread 0.6667、stdev 0.3333 |

判决：**Δ = −16.67，p = 1.00**——工具写的是「演化臂**更差**」，汇总行写的是「1/1 格**有演化但分不开**（不显著或方向不对）——**不能**据此说演化带来了提升」。逐条失分率：基准臂 **0% / 0% / 0%**，演化臂 0% / **25%** / **25%**。

**基准臂从 mean 0.5833（1800s）/ 0.4167（3600s）直接顶到 1.0**——四发全中、一发不漏、零分布宽度归零。**这才是这一轮真正量到的东西**：前两轮「演化臂更差」的读数，大部分量的不是「手册好不好」，而是**那颗地雷**——地雷同时压两臂，而手册写着「渲染走工具面」的那一臂踩得更多（演化臂 4/4 全踩、基准臂 1/4）。工具面一修，两臂同时松开，基准臂直接满分。

演化臂剩下的那点失分**也不是「做得更差」**：r3、r4 两条撞了 3600s 上限（`exit 124`），而演化臂的事件数是基准臂的近两倍（546 / 1219 / 890 / 770 对 534 / 609 / 656 / 558）——手册让它走完整的工具面渲染路径（fetch-fonts → assemble → render → audit-charset → verify-colors），**做的事情更多，于是更容易撞钟**。r3 的失分证据直接写着「`probe.html`：画面上找不到那句旁白」——它被掐死时交的是**探针页，不是成品页**；r4 同样撞钟，却已经把成品交出来了，照样判满分。

**但这一格从设计上就测不出手册的价值**，两条独立的原因：

1. **天花板**：判据是 0/1 的，基准臂已经 1.0，**Δ 的上限就是 0**——演化臂再准也只能是 1.0。**工具自己就写了这句话**：「基准臂没有失分项——这一格没有可测的效应」。
2. **题面已经把手册要教的东西写出来了**：题面原文写着「旁白就是配音要念的那一句——**画面上的句子必须跟它逐词对上，冠词、助词一个字都不能少**」。手册里被这一格量到的那条（旁白一字不改），**题面已经给了**；手册额外教的四条——词形墨迹占比阈值（≥12% / ≥30%）、逐字着色三色、「同一份字符串存一次」的做法、可复现说明 + 交卷前自检——这一格的三条判据**一条都不量**（判据只认两个结构事实：「有没有一个元素的可见文字恰好等于那句旁白」「词形有没有独立于那句话成元素」）。

所以第三轮的诚实读法是：**「手册这个杠杆」这一问仍然没有证据，而这一格也不再是能给出证据的地方**——要量它，得先把规则从题面里拿掉、再换一道还有余量的题。这一轮真正的收获是另一件事：**地雷被挖出来了、修好了、并且被量到了它的代价（两臂都被压在 0.42–0.58，修完基准臂直接满分）**。

#### 两条始终要说清的话

1. **功效远远不够**：`arms.py` 自己算的数是——要把 +16.7 分的效应测出来需要 n=21，按「实跑建议 ×1.5」就是 **n≈32/臂**；现在 n=4。所以「读不出」是**本来就读不出**，不是「仔细读了也没发现」。
2. **基准臂自己的零分布宽度一路收缩，工具面修好后直接归零**：1800s 那轮 4 次 rollout 给出 0 / 0.33 / 1 / 1（极差 1.0）；3600s 那轮是 0.33 / 0.33 / 0 / 1（均值反而从 0.58 掉到 0.42——**多给时间并没有让基准臂变好**）；工具面修好后是 1 / 1 / 1 / 1（**spread 0、stdev 0**）。三轮读数各自作废（上限变了、工具面变了），但它们合起来指向同一件事：**压着分数的是环境，不是树**。「没有零分布就没有『提升』这个说法」这条纪律，这一格又印证了一次。

## 五、跑批过程中修掉的两个真缺陷

### 5.1 B 线：相对 run root 会让一次 rollout 静默死掉（`garage-ii/usine_adapter.py`）

`--root` 传相对路径时，argv 里传给 `dsh_run.mjs` 的全是相对路径，而**子进程的 cwd 是 workspace**（不是发起进程的工作目录）——任务文件被解析到 `workspace\..\garage-ii-result\..`，读不到，rollout 当场死。

症状很有欺骗性：臂记录里写的是**「判据跑不成（不是零分）」**，而 run 目录里多出一层同名嵌套目录（`events.jsonl` 落在里面），看起来像「模型没干活」。

修法：run root 在适配层构造时就 `resolve()` 成绝对路径；离线自检（`garage-ii/smoke_dsh_bridge.py` 的 `[6b]`）钉住「传给 `dsh_run.mjs` 的路径全是绝对的」。

### 5.2 B 线：repeat 相位与 sweep 相位用的不是同一把锁

`_phase_sweep` 与 `_phase_reselect` 的锁在 `<root>/adapt/.sweep.lock`，而 `_phase_repeat` 的锁在 `<root>/.sweep.lock`——**两个不同的文件**。锁的本意是「同一个 root 上不许同时跑两个跑批」（产物会互相覆盖而且不报错），现在两个相位各锁各的，等于没锁到同一件事上。

## 六、结论

**问题**：RSIAgent（A 线）与 harness2（B 线）能不能改进 `usine`，让新生成的 `usine\examples\foodnames-ii-*` 解决旧成片的问题？

**一句话答案**：**A 线能，而且改进已经落成真提交、并产出了新一代 12 期成片**——旧 12 期的 **954 条版式不达标 + 54 处音画不同步**，现在是 **0 / 0**，成片在 `usine/examples/foodnames-ii-ep01-sushi … foodnames-ii-ep12-fries`（每期两画幅成片 + 海报 + 三版封面 + 旁白 + 床 + 三平台发布词，`video_layout.json` 的 `failures` 全 0，发布侧两道门全绿）。**B 线这一轮没有证据说 harness2 能自演化出更好的东西**——sweep 连一棵演化树都没交出来（§4.4），手写的演化树跑了三轮也读不出提升（§6.2）；但它**查出了一个真缺陷并且修好了**：工具面里叶子读 stdin 会**永久阻塞**，把整条 rollout 的时间预算烧光——这是**跑批量出来的副产品，不是分数换来的**（§4.6）。两边的结论分别是「**A 线的杠杆直接落在已交付的成片上**」与「**B 线的杠杆落在智能体现场，但这一格已经测不出它**」。

### 6.1 A 线：能——而且改进是**真提交**，不是建议清单

波 5 的产出是真提交（`6985542`，tag `theatre/wave-1`）：出题席出题 → Actor 改代码 → 验证席判 → 合并器合进仓库。改的是 D1–D5 五处真缺陷（画面句子被改写、词形不是主角、暗词看不清、高亮色不是品牌色、空白带过大）。

同一套判据、同一批 12 期数据、12 语种 × 2 画幅 = 144 个组合：

| 量 | 之前 | 之后 |
|---|---|---|
| 画面句子 != 配音句 | **54 处不一致** | **0**（144/144 逐词一致，句子门 exit 0） |
| 版式不达标 | **954 条** | **0 条** |

分项（每项按两画幅计）：`hero_prominence` 126 → 0、`token_readable` 288 → 0、`highlight_brand` 288 → 0、`no_big_empty_band` 144 → 0、`sentence_matches_voice` 108 → 0。

**尺子换过两次，两侧都用新尺子重测**：① 像素层从隔行抽样改成逐行扫（原尺子漏掉 1.5px 的页脚细线，把两段空气并成一段——13 条里有 12 条是假阳性）；② 竖屏拟合框 960 → 800（最后那 1 条**真实**的空带 15.26% → 14.48%）。

**成片**：12 期全部跑完、零失败，两画幅成片 + 海报 + 三版封面 + 旁白 + 床都在 `usine/examples/foodnames-ii-ep01-sushi … foodnames-ii-ep12-fries`；每期 `video_layout.json` 的 `failures` = **0**（12 期 × 2 画幅 × 12 语种 = **288 条检查条目**全过）。上面那张表的两个数是**从盘上的报告重新读出来的**，不是抄上一轮的结论：旧 12 期的 `failures` 逐期 77 / 78 / 83 / 82 / 79 / 82 / 83 / 79 / 76 / 77 / 81 / 77 = **954**，新 12 期 = **0**。**发布侧也补齐了**：12 期的 `publish/` 各 8 个文件（三份平台原稿 + `facts.json` + 三份 `copy-*.md` + `manifest.json`），两道发布门禁（`feuille copy check --facts` 的 8 条机检 + `feuille publish check-plan`）**12 期全绿**——做法与那条「内容可带、规格必重取」的边界见 §三之七。

### 6.2 B 线：sweep 没演化出树；手写的演化树**三轮都没测出提升**——但第三轮量到了地雷的代价

sweep 跑完但**没有产出任何演化树**（§4.4）：四个候选的树差异都是空文件（一个改了可编辑面之外的文件、一个被网关 502 吃掉、四条 rollout 全部超时）。按 `arms.py` 的零格规则，那一轮的 compare 只能判「演化**没动这一格**——构造上的零」。

所以**「harness2 自演化有没有用」这一问，这一轮没有证据**。但「harness 树这个杠杆有没有用」可以单独量：手写一棵演化树（基准树 + 一份 foodnames 手册，§4.5），用同一道判据、同一道题、同一个模型跑 n=4，与基准臂的零分布并排读。**上限变了旧读数就作废**，所以一共跑了三轮：

| 轮次 | 基准臂（零分布） | 演化臂 | Δ | p | 工具的判决 |
|---|---|---|---|---|---|
| ① 上限 1800s | 0.3333 / 1.0 / 1.0 / 0.0（0.5833） | 0.0 / 0.3333 / 0.0 / 0.0（0.0833） | −50.0 | 0.99 | 演化臂更差 |
| ② 上限 3600s | 0.3333 / 0.3333 / 0.0 / 1.0（0.4167） | 0.0 / 1.0 / 0.3333 / 0.0（0.3333） | −8.33 | 0.76 | 演化臂更差 |
| ③ 工具面修好后（仍 3600s） | **1 / 1 / 1 / 1（1.0）** | 1 / 1 / 0.3333 / 1（0.8333） | −16.67 | 1.00 | 演化臂更差 |

**三轮都不是「手册让智能体变差」**，第三轮把机制查实了：

- ①② 两轮读到的差，**大部分是工具面里那颗地雷**：`poster fit-diag` 缺参数时去读 stdin，而工具面是同进程派发叶子、stdin 是宿主那根永远不关的管道 → 永久阻塞，烧光整条 rollout 的预算。两轮 16 条 rollout 里 9 条卡在工具调用，8 条卡在这**同一个**调用上；手册写着「渲染走工具面」的那一臂踩得更多（4/4 对 1/4）。修掉之后（边界层 `FEUILLE_STDIN=off` + 叶子缺参数立刻 exit 2，CLI 那条路一个字没改），第三轮 **8 条 rollout 没有一条停在工具调用上**（21 次 `fit-diag` 调用全部当场回结果，未回 0）。
- ③ 修好之后的读数是**基准臂 4/4 全满分、零分布宽度归零**（spread 0、stdev 0）。工具自己写了一句要紧的：「**基准臂没有失分项——这一格没有可测的效应**」。**天花板**：判据是 0/1 的，基准臂 1.0 ⇒ Δ 的上限就是 0。
- 演化臂剩下的那点失分来自 **r3、r4 两条撞 3600s 上限**（`exit 124`）：手册让它走完整的工具面渲染路径，做的事情更多（事件数 1219 对基准 609），于是更容易撞钟。r3 被掐死时交的是**探针页不是成品页**（「画面上找不到那句旁白」）；r4 同样撞钟，却已经把成品交出来了，照样判满分。

**结论是「这一格读不出手册的杠杆」，不是「手册有害」**；而且这一格**也不再是能给出证据的地方**：题面原文已经写着「画面上的句子必须跟它逐词对上，冠词、助词一个字都不能少」——被量的那条规则**题面已经给了**；手册额外教的四条（词形墨迹占比阈值、逐字着色三色、「同一份字符串存一次」的做法、可复现说明 + 交卷前自检）这一格的判据**一条都不量**。要量它，得**先把规则从题面里拿掉**、再换一道还有余量的题。

**这一轮 B 线真正的收获不是分数，是那个真缺陷**：它是**跑批量出来的**——两臂 16 条 rollout 的卡点普查把「叶子读 stdin 会永久阻塞」这条挖了出来；修掉之后两臂同时松开、基准臂直接满分。而这条缺陷在合并门禁里**没有钉子**（`vitest.config.ts` 的 include 只覆盖 `packages/*/test/**`，`tools/` 里的产线脚本不在门禁视野内）。修法**掐在边界**：`packages/dsh-plugin/src/capture.ts` 设 `FEUILLE_STDIN=off`，`packages/poster/src/fit_diag.ts` 与 `packages/poetry/src/audio_profile.ts` 缺参数立刻 exit 2 + 用法错，**CLI 那条路一个字没改**（本轮实测五条路径：文件参数 → 0 / 管道 `-` → 0 / 管道老用法 → 0 / 文件不存在 → 2 / 工具面空参 → 2）。

### 6.3 两条线的杠杆不一样，报告里不许含糊

- **A 线改产线代码** → 直接决定已交付的 12 期成片（这一轮就是它交付的）。
- **B 线改 harness 树** → 改的是「智能体现场怎么搭一个场景」。要落到已交付成片上，还得有人把 harness 里的版式知识搬进 `build_episode.mjs` / `templates/video_style.css`。

### 6.4 这一轮顺带修掉的四个真缺陷

1. **合并带进来的韩语回归**：波次把视频侧的韩语改成 `.cv` 融合渐变，代价是 `poster audit-charset` 当场红、**整条产线在第 12 步停住**，而且韩语丢掉页脚图例承诺的元音/辅音分色。修法：视频侧继续用实测补丁，`.cv` 只留给融合音节。
2. **尺子自己的缺陷**：隔行抽样漏掉 1.5px 细线 → 13 条里 12 条是假阳性（详见 §三之四）。
3. **渲染环境的视口亏空**：Edge 144 的 headless 窗口比视口高 93 CSS px，产线那条 `poster render` 从不补偿 → 画布底部 93px 渲成底色 → 12 期全卡在第 14 步（详见 §三之五）。
4. **工具面里叶子读 stdin 会永久阻塞**：`poster fit-diag` / `poetry audio-profile` 缺参数时 `readFileSync(0)`，而 dsh 的工具面是**同进程**派发叶子，stdin 是宿主那根永远不关的管道 → 一条 rollout 的时间预算被整个烧光、什么也交不出来（实测 16 条 rollout 里 9 条卡在工具调用，8 条卡在这同一个调用上；演化臂 4/4 全踩）。修法**掐在边界**：`FEUILLE_STDIN=off` + 叶子缺参数立刻 exit 2，CLI 那条路一个字没改（详见 §4.6）。

### 6.5 这一轮**没有**解决的（写在明处）

- **guest 里那道结构门是环境性红**——不是缺陷（§三之三），本轮决定不动它。
- **B 线的 sweep 基础设施**：引擎是零补丁的 vendored fork，`fcntl` 只能在适配层垫；提议者这一轮交不出树（三个原因都在 §4.4），所以 B 线的「自演化」这一问仍然是空的。
- **B 线的「harness 树这个杠杆」三轮都没读出提升**：手写演化树 n=4 对基准 n=4，三轮 Δ = −50.0 / −8.33 / −16.67，p 全在 0.76–1.00。第三轮把上限挪到 3600s、又把工具面的地雷修掉之后，**基准臂直接 4/4 满分、零分布宽度归零**（§4.6）——这一格**已经测不出东西了**：判据是 0/1 的，基准臂满格 ⇒ Δ 上限为 0；而且题面自己就把「旁白一字不改」写出来了，手册多教的那几条判据一条都不量。要量它，得**先把规则从题面里拿掉**、换一道还有余量的题，再把 n 提到 32/臂。
- **渲染环境翻转的读数可比性**：新旧读数跨了一次渲染环境翻转（§三之五，旧 12 期渲于 10-20 01:10–02:29，之后就切了）。这一条**只可能影响**「最大空白带」那类纯像素几何判据；其余四类（不透明度、高亮色、句首词是否被改写、句子的逐词一致性）与浏览器无关——954 条里 810 条属于后者。另有一点已经查实：**这份文档第一版把破口归给「Chrome 155自动升级」，实测推翻了**（产线用的是 Edge 144，Chrome 压根没被调用）。
- **渲染环境翻转的触发条件没定位到**：已知同一份 HTML、同一枚 Edge 二进制、同样的渲染参数，10-20 渲得完整、之后渲不全；翻转发生在显示/桌面会话/DPI 布局中的哪一项上，这一轮没查出来。修复改成**运行时实测亏空**之后就不再依赖它，但「什么变了」仍是一个悬案——它会再翻一次。
