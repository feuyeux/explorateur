# 多平台发布手册（抖音 / 小红书）




> **什么时候读这份文档**：要把 `build/scene/scene-colors_*.mp4`（或任何成片）发到
> 抖音 / 小红书创作服务平台时。渲染相关的坑在 [render-handbook.md](render-handbook.md)，
> 这里只管「成片出去以后」这一段。
>
> **知乎专栏不在这份文档里**。知乎走的是「Markdown 导入文档 + 内嵌视频 + 改已发布链接」，
> 富文本机制与抖音 / 小红书完全不同（知乎是 Draft.js，转换只在 paste 事件触发），
> 流程与踩坑见 [zhihu-publish-playbook.md](zhihu-publish-playbook.md)。
>
> **问「效果怎么样」看 [metrics-playbook.md](metrics-playbook.md)**——两平台创作中心的
> 取数入口、关键指标字段、判读基准，以及 2026-10-06 的基线数值。

## 0. 发布前必查：封面不能省

**用户硬性要求（2026-10-06）：每支视频发布时必须带封面。**

发布表单里的「设置封面」是**必查项**，不是可选项：

- **小红书**：封面是列表页唯一的视觉入口，**封面点击率是这里的关键指标**（metrics-playbook §3.3）。
  不设封面就用平台默认截帧，点击率会直接拖垮分发。
- **抖音**：封面进信息流与主页，同样影响 `封面点击率`（基线 35%）。

**操作顺序**：`上传视频 → 设置封面 → 填标题正文 → 选合集 → 发布`。
设封面在填文案之前，别等填完了才想起来回头找。

> **能力边界**（坑 ㉗）：自定义封面图**传不上去**——
> 小红书只接受从视频里截帧（平台机制），抖音是 `upload_files` 的工具限制。
> 所以「带封面」在当前能力下落地为：**在表单里显式确认封面已选定**（截帧或平台推荐），
> 而不是静默跳过这一步。若某支最终用的是平台默认封面，**要在发布记录里写明**。

>
> **本文档的每条流程都经过实跑验证**，不是从平台文档抄的。带 ⚠️ 的是「不照做就出错」的点。

## 2. 硬性限制对照

| 项 | 抖音 | 小红书 |
|---|---|---|
| 标题上限 | 30 字 | **20 字** ⚠️ |
| 正文上限 | 1000 字 | 1000 字 |
| 合集标题上限 | 20 字 | 20 字 |
| 合集简介上限 | 200 字 | **50 字** |
| 视频上限 | — | 4 小时 / 20 GB |
| 正文编辑器 | Slate（`contenteditable`） | ProseMirror / tiptap（`contenteditable`） |
| 「第 N 集」编号 | **平台自动分配，不要手动设** | 同左 |

⚠️ **抖音的 29 字标题原样搬到小红书会红字报错**（显示 `28/20`）。

**标题方案按平台字数倒推**，不要把抖音标题搬过去再修：

| 方案 | 形态 | 例 | 字数 |
|---|---|---|---|
| 抖音（≤30） | `系列名｜第NN话 语种：场景` | `四种语言数数｜第01话 俄语：老院子廊下数灯笼` | 满预算 |
| 小红书（≤20） | `系列名｜NN语种`（**砍掉「第」「话」「：」和场景关键词**） | `四种语言数数｜04粤语` | 省出预算 |

⚠️ colors 批次的小红书标题是 `14种语言聊颜色｜NN语种 场景关键词`（19 字），
numbers 批次进一步砍成 `四种语言数数｜NN语种`（11 字）。
**每批都要按当期标题文案文件实测字数，不要沿用上一批的形态。**

## 3. 跨平台铁律

1. **一次只发一个 Browser action，绝不并行。** Browser action 共享页面/快照/navigation 状态，
   并行会互相踩。
2. **`click` 返回 `effect.verified: false` 不代表没生效**，只代表「输入已投递、效果未验证」。
   必须 `inspect` / `query` / `screenshot` 复核后才能声称成功。
3. **`fill` 返回 `ACTION_EFFECT_MISMATCH` 也不代表失败**（见坑 ④⑤）。永远以
   `query kind=dom` 读回的 DOM 为准，不相信返回值的 `success` 字段。
4. **元素 ref 是 snapshot-scoped 的。** 导航 / reload / 重新 inspect 之后，旧 ref 全部作废，
   必须重新取。绝不复用上一轮的 ref。
5. **发布成功判据**（两个都要）：URL 出现 `published=true` **且** 表单重置为上传页。
   **草稿箱计数不是判据**——见坑 ⑭。权威判据是**回列表核验到这条作品**（坑 ㉖）。
6. **合集旁证分平台**：
   - 抖音：合集详情页「总集数」递增（`/content/manage?tab=collections` 能读到）。
   - 小红书：**这个旁证不成立**——笔记管理页没有合集 tab（见 §5.1），
     只能回笔记管理列表按标题核验。
7. **上传后不要先 sleep**。表单字段立刻就渲染，视频还在「上传中」；
   旧流程的 `Start-Sleep 25` 反而会让页面重建、作废刚取的 ref。正确顺序见 §4.2 / §5.2
   与坑 ㉒。**（本条曾长期与坑 ㉒ 矛盾，以坑 ㉒ 和 §5.2 步骤 3 为准。）**
8. **批量发布前先跟用户确认一次整批**，拿到确认后同批内不必逐支再问；
   但只要**页面刷新、换账号、草稿被改动**，就要重新确认。

### 3.1 元规则一：每一步都必须自带判据

**这是本手册存在过、但一直缺失的一层。** numbers 批次（2026-10-06）之所以在坑已经
写得很全的情况下还是返工两轮、烧掉一整个下午，根因不是坑不够多，而是：

> **被执行的是「流程步骤」，不是「坑列表」。步骤本身写错时，坑列表救不了。**

§5.2 第 6 步原文写的是「`Tab` → 关掉话题联想面板」，但 `Tab` 根本不关面板。
执行者严格照做，第 6 步之后直接点发布，**必然中招**——坑 ㉛ 写得再细也没用，
因为没人会在照着步骤做的同时再去翻坑列表。

所以规则是：**§4.2 / §5.2 的每一步都必须带一个可观测判据，写在同一行的「判据」列里。
没有判据的步骤等于没写。**

判据的三个要求：

| 要求 | 说明 | 反例 |
|---|---|---|
| **可观测** | 有一次 `query` / `screenshot` 能读出来 | 「确认已选」——读不出来 |
| **廉价** | 一次调用，不超过 3 秒 | `inspect` 整个发布页（超 64 KiB 预算，坑 ⑨） |
| **二值** | 能明确判「是/否」，不产生「大概是」 | 「看起来正常」 |

**判据永远优先于返回值。** `success: true`、`verified: false`、按钮转没转 loading，
都是旁证；只有回读到的状态是证据（坑 ⑤）。

### 3.2 元规则二：成功次数不能证明流程正确

§5.2 曾经把标题写成「**已验证序列，05–14 实跑 10/10**」。这句话是**有毒的**：

numbers 批次的 02、03 两支确实一次过，但**不是流程生效**——`Tab` 和点发布之间隔着
`ask_user` 往返的几十秒，面板在那段时间里被别的东西顺带关掉了。**这是运气。**
如果把「10/10」当成因果，04 就会照着做、然后翻车（它确实翻了）。

> **只有当每一步都有独立判据时，「连着成功 N 次」才是证据。**
> 否则它只是「N 次都没被抓到」，不是「N 次都做对了」。

推论：**流程里凡是靠时序、靠运气、靠「反正会自己好」成立的环节，都必须换成显式判据。**
本批唯一奏效的修复（点非话题段落）之所以可靠，正是因为它有独立判据
（`.tippy-box` 报 `Element not found`），不依赖任何时序。

### 3.3 元规则三：排查要有止损线和落盘纪律

**（1）负结果即时落盘。** 每排除掉一个手段，当场写进坑 ㉛ 那样的「已排除」表，
**不要攒到会话末尾**。理由很实际：本批发生过上下文压缩，压缩后的恢复摘要里
负结果表不完整，于是 `hover` 这条已经被证伪的路又被补试了一遍。
**负结果比正结果更容易丢，因为它「什么都没发生」，不值得被写进摘要。**

**（2）修复不收敛就止损重做。** 止损条件：**同一个修复动作连试 2 次仍不收敛，立刻停手**，
不要试第 3 种修法。理由是编辑器污染的修复是**开放式搜索**——每种修法都可能在
修坏的地方制造新问题，收益递减而风险递增。04 首次尝试的修复循环就该在这里结束。

**（3）被污染的表单不要在上面继续修。** 污染的正文意味着「当前 DOM 状态不可信」，
在上面继续操作是在不确定的基础上叠加不确定。**正确动作是开新发布页重做整支**：
重做一支的成本（上传 + 填两个框）远低于「修好一支被反复污染的表单」。

**（4）改流程 > 改内容。** 发现问题先问「哪一步的判据缺失」，再问「怎么把这支复好」。
顺序反了就会陷入无限修复循环。

**（5）每批发布后跑一次文档自洽检查。** 本手册把同一条知识写在好几个地方
（铁律 / 流程步骤 / 坑 / 核验清单 / 台账），**它们会各自漂移**。
numbers 批次复盘时一次就抓出两处直接矛盾：

| 矛盾 | 后果 |
|---|---|
| 铁律 7「上传后必须等转码 25 秒」↔ 坑 ㉒「上传后别急着睡 25 秒」 | 照铁律做就会撞上 `STALE_ELEMENT_REF` |
| 铁律 5 + §7「草稿箱计数为 0」↔ 坑 ⑭（已被证伪） | 照着判会把**成功报成失败**，进而触发重发 |

**所以：同一条知识只能有一个权威位置**（流程步骤），其他地方只允许引用，不允许复述。
每批发布收尾时用 `grep` 把关键判据串全检一遍：

```bash
grep -n '草稿箱\|Start-Sleep\|10/10\|已验证序列' docs/publish-playbook.md
```

凡是命中且**没有**紧跟「以 §X 序列为准」这类指向的，就是漂移了，要修。

## 4. 抖音发布流程

### 4.1 前置：合集必须先建

⚠️ **抖音的合集入口只有创建页一个，且创建页只列「已发布作品」**。所以顺序是：

```
内容管理 → 合集管理 → 创建合集（可以建空的）→ 再逐支发布时在发布页勾选
```

发布页的「添加至合集」下拉**没有新建入口**，空合集必须提前建好，否则下拉里根本看不到它。

### 4.2 逐支发布（每一步都自带判据，见元规则一）

| # | 动作 | 判据（不信返回值，只信这一列） |
|---|---|---|
| 1 | `navigate` 发布页（`replaceCurrentTab: true`） | 单标签页流程 |
| 2 | `query kind=semantic` text=`上传视频` → 取上传卡 ref | 拿到上传卡 ref |
| 3 | `upload_files` paths=[`build/scene/scene-<scene>_<locale>.mp4`] | `success: true`。**不要预先 `stat`/`ls`**（坑 ⑬） |
| 4 | `bash: Start-Sleep -Seconds 25` | 等转码 |
| 5 | `query kind=editable` | 取到标题 input + `.zone-container[contenteditable="true"]` 两个 ref |
| 6 | `fill` 标题 | `textLength` = 目标字数（上限 30） |
| 7 | `fill` 正文 | ⚠️ **末尾保留一个尾随空格**，见坑 ① |

| 9 | `query kind=semantic` text=`请选择合集` → click | 合集下拉展开 |
| 10 | `query kind=semantic` text=`<合集名>` → click | |
| 11 | `scroll` down 900 | |
| 12 | `screenshot` | 复核：合集名已选 / 允许下载 / 公开 / 立即发布 |
| 13 | `click` 发布 | 位置随 viewport 变，见下 |

**发布按钮坐标**（`click position`，绝对 CSS 像素）：

## 5. 小红书发布流程

### 5.1 前置：合集在第 01 支的表单里一次建好

⚠️ **小红书笔记管理里没有合集 tab，头像菜单里也没有**。合集只有一个入口：

```
发布笔记 → 加入合集 → 选择合集 → 创建合集
```

点「创建并加入」可以**一次完成建集 + 挂到当前这支**。这跟抖音正好相反
（抖音要先建空集，小红书可以边发边建）。

本项目的合集就是在第 01 支的表单里创建的，之后 13 支只需在下拉里点第一位。

### 5.2 逐支发布（每一步都自带判据，见元规则一）

> ⚠️ 本表**不再标注「实跑 N/N」**。numbers 批次的 02/03 一次过是运气不是流程
> （面板被 `ask_user` 往返顺带关掉了），详见元规则二。**相信判据，不要相信次数。**

| # | 动作 | 判据（不信返回值，只信这一列） |
|---|---|---|
| 1 | `query kind=semantic` text=`上传视频` limit≥10 → 取 `class` 含 `upload-button` 的 ref | ref 的 `class` 里含 `upload-button` |
| 2 | `upload_files` paths=[`build/scene/scene-<scene>_<locale>.mp4`] | 返回 `success: true`（这一步返回值可信） |
| 2b | **设封面**（非豁免批次必做，见 §0） | 表单里出现「设置封面」卡片 → 选帧或用「智能推荐封面」→ **回看该卡片缩略图已变**。⚠️ 位置在**填文案之前**（§0） |
| 3 | `query kind=editable` → 取标题 input + `.tiptap.ProseMirror` ref | 拿到 2 个 ref。**不要先 sleep**（坑 ㉒） |

| 17 | `bash: Start-Sleep -Seconds 6` | |

| 19 | 回笔记管理列表核验 | 列表里有这条标题才算成功（坑 ㉖）。**这是唯一的权威判据** |

## 6. 踩坑实录

### 坑 ① 抖音正文末尾标签被联想面板吃掉（已造成线上事故）

**现象**：抖音第 01 支英语的正文发出后是 242 字，正确版本只有 124 字。实际内容 =
`[完整正文] #语言学习 #X[重复整段正文] #语言学习 #多语言对比 #英语口语 #英语学习语言对比
#英语口语 #英语学习 #小语种就业前景`。

**原因**：正文末尾的 `#小语种` 在 blur 时被 Slate 识别成话题候选，弹出联想面板并**选中了一个
无关联想词**（`就业前景`）；随后 `fill` 的插入语义导致原文被重复追加。

**解法**：⚠️ **正文最后一个标签后面必须留一个尾随空格**。尾随空格让 Slate 判定话题未闭合，
联想面板不弹，标签保持纯文本。第 03 支起验证有效。

**教训**：话题/标签类富文本，**一律在末尾加尾随空格**，抖音、小红书都适用
（小红书用 `Tab` 方案，见坑 ②）。

### 坑 ② 小红书话题联想面板会替换末尾标签

**现象**：填完正文，正文末尾的 `#小语种` 变成一个 `.suggestion` 装饰 span，内容被替换。

**解法**：填完正文立刻 `press_key key=Tab`。`.suggestion` 装饰 span 消失，
标签文字保持不变。第 01–04 支均验证有效。

⚠️ **`press_key key=Escape` 无效**，面板仍在。别浪费时间试 Escape。
⚠️ **`hover` 到别处也关不掉**——这个面板不是 hover 触发的，鼠标移开它照样挂着。

**复核方式**：`query kind=dom` selector=`.tiptap.ProseMirror`，确认末段是纯文本、没有
`<span class="suggestion">`。

> ⚠️ **`Tab` 只解决「span 变纯文本」，不解决「面板消失」**——这两件事被同一个 `Tab`
> 混淆了整整两轮返工。面板还开着就去点发布，会被坑 ㉛ 吞掉。

### 坑 ③ 小红书正文 `fill` 必然返回 `ACTION_EFFECT_MISMATCH`

富文本归一化后 DOM 文本与请求值不完全相等（换行变成 `<p>`、尾随字符被 trim）。
**这是正常的**。`effect.textChanged: true` + `textLength` 接近目标值即可，
真正的判据是随后 `query kind=dom` 读回的 HTML。抖音正文 `fill` 同理。

### 坑 ④ 抖音 `fill` 对非空 contenteditable 是插入不是覆盖

往已有内容的编辑器里 `fill` 会**追加**而不是替换。清空方式按平台分：

- **`Control+a` 在注入通道不生效**（原记录，只有这一条时靠 `drag` 拉选 + `Backspace` 做两轮兜底）；
- **macOS 上 `Meta+a` + `Backspace` 一次就干净**（2026-10-06 实测）——
  清完 DOM 塌回单个空 `.ace-line`，`data-placeholder` 回到「添加作品简介」，
  `data-node="true"` 的行只剩 1 条。**先试 `Meta+a`，不行再退回 `drag`。**

第 01 支正文污染事故的第二重成因就是这里。检测与补救见坑 ㉙。

### 坑 ⑤ `click` / `fill` 的 `success: true` 都不是效果证明

`click` 的 `effect.verified` 恒为 `false`。所有「点了之后到底生效没有」的问题，
一律靠 `inspect` / `query(kind=text|dom)` / `screenshot` 回答。

### 坑 ⑥ 小红书发布页内层滚动容器不能用 `scroll` action

`scroll` 返回 `moved: false, atEnd: true`，但页面明显还能往下滚——只是滚的不是它认定的那个容器。

**解法**：先让页面获得焦点（点一个中性区域或 `Tab`），再 `press_key key=PageDown`。
另外 `press_key key=PageUp` 有时完全无效（焦点不在滚动容器上），此时改用
`query` 读 DOM 复核内容，不要反复试滚动。

### 坑 ⑦ 抖音合集与小红书合集的建立方式相反

| | 建空集 | 表单里建集 | 笔记管理里有合集 tab |
|---|---|---|---|
| 抖音 | ✅ 必须 | ❌ 无入口 | ✅ `?tab=collections` |
| 小红书 | ❌ 无此路径 | ✅ 「创建并加入」 | ❌ **没有** |

不知道这点会在抖音卡住（空合集不预建，下拉里永远看不到目标合集）。

### 坑 ⑧ 抖音审核中的作品不能提交编辑

第 01 支首次尝试修改时因审核中，「提交修改」不可用。**等审核状态变「通过」再改**。
这也是为什么第 01 支的修正在 14 支全部发完、全部通过之后才做。

### 坑 ⑨ `inspect` 可能返回 `BROWSER_RESULT_TOO_LARGE`

发布页 DOM 很大，`inspect` 会超 64 KiB 预算。**改用定向查询**：
`query kind=editable`（取输入框）、`query kind=semantic`（按可见文字定位控件）、
`query kind=text` + 窄 selector（读内容）。不要反复重试 `inspect`。

### 坑 ⑩ `screenshot` 可能返回旧帧

连续截图字节数几乎相同时，说明抓到的是同一帧。**同状态下 DOM query 与 screenshot 矛盾时，
以 DOM query 为准**。判断「页面变了没」用 `query`，`screenshot` 只用来读布局和视觉状态。

### 坑 ⑪ 阿拉伯语 / 希伯来语正文里的「查到」是错字

`从红色一路查到白色` 应为 **`问到`**。抖音 09、10 两支已带这个错字发出，
小红书版已改对。两平台都是 RTL 语种，错字来源相同，属笔误而非 RTL 排版需要。

### 坑 ⑫ 用户可能同时操作同一个浏览器面板

焦点会漂移，出现重复操作或漏操作。**每次动作前用 `query` 确认页面仍在预期状态**，
不要凭上一轮的记忆继续。

### 坑 ⑬ 上传前不要用 shell 校验文件路径

`upload_files` 自己会校验存在性、类型、授权、数量、体积。
预先 `stat` / `ls` / `test` 是浪费，且可能因路径写法差异产生假阴性。

### 坑 ⑭ ~~小红书草稿箱计数是发布成功的免费校验~~ **这条是错的，2026-10-06 已推翻**

**原记载（错）**：发布后草稿箱应回到 `(0)`；计数增加说明那支没发出去、留成了草稿。

**实测反证**：numbers 批次四支**全部发布成功**，草稿箱计数却单调上涨：

| 时点 | 已成功发布 | 草稿箱 |
|---|---|---|
| 01 发布后 | 1 支 | `(1)` |
| 02 / 03 发布后 | 3 支 | `(3)` |
| 04 发布后 | 4 支 | `(4)` |

**根因**：小红书在**编辑过程中就自动存草稿**，发布成功后**草稿不会被清理**。
所以草稿箱里堆的是**编辑过程的残留**（包括 01/02/04 几轮返工留下的坏表单），
与「发布成功与否」**没有对应关系**。

**为什么这条错误特别危险**：它被写进了「跨平台铁律」第 5 条和 §7 核验清单，
也就是**被执行者当作发布成功判据**。照它判会把**成功的发布报成失败**，
进而触发「重发」——那是会真的产生重复作品的错误。

> **教训比修正更重要**：一条没被证伪过的「经验」，比没有这条经验更糟。
> 它会以权威口吻提供错误的判据，让执行者**主动做出错误决策**。
> 这就是元规则一（每步自带判据）和元规则二（成功次数不能证明流程正确）要防的东西。

### 坑 ⑮ 上下文压缩会让 Browser skill 加载凭据失效

长流程里如果发生过上下文压缩，**压缩后必须重新 `skill` 一次
`browser-use:control-in-app-browser`**，否则 Browser 调用返回 `SKILL_REQUIRED`。

### 坑 ⑯ `open_tab` 传入的 URL fragment 不会生效

会沿用上一次的 hash。要验证 `#hash` 深链必须让页面自己跳（壳页 `location.replace(...)`）。

### 坑 ⑰ 正文标签里的易混码位

`；`(U+FF1B) vs `;`(U+037E 希腊问号)、全半角问号、`-`/`–`/`—`、各类引号——
在发布文案里写这些字符时，**编辑完立刻回读该行打印码位确认**，别靠肉眼看 diff。
写检查脚本本身时尤其危险：脚本里的字面量被静默归一，会导致验收永远误判。

### 坑 ⑱ 平台频率限制

单日连发 14 支会触发频率风控。本项目 2026-10-03 抖音 14 支、2026-10-04 小红书分批
均未被限流，但这是**用户明确接受的风险**，不是平台保证。换时间窗发更稳。

### 坑 ⑲ 合集下拉被视口裁掉 = 查不到任何选项

**现象**：`选择合集` 按钮点击「成功」，但紧接着查合集名返回 `matchCount: 0`——
看起来像下拉没打开，或合集不存在。

**真实原因**：合集下拉**向下展开**。按钮在视口底部时（实测 y=986 / 视口高 1029），
下拉整体落在视口外，DOM 里有、屏幕上没有。

**解法**：点之前先看按钮 rect，**y > 视口高 - 120 就先 `press_key PageDown`**，
把它抬到视口上半部再点。抬到 y≈142 后下拉落在 y≈181，稳定可查。

⚠️ 这是「查不到」的假阴性。**不要**因为 `matchCount: 0` 就去改代码或怀疑合集被删。

### 坑 ⑳ 合集有没有选中，看 class 变没变

比截图可靠，也比读全页文本省一次大查询：

| class | 含义 |
|---|---|
| `collection-plugin-button` | **未选**。下拉关闭时查合集名 → `matchCount: 0` |
| `collection-plugin-choose` | **已选**。同时 `class="collection-name"` 显示名字 |

选完关掉下拉，查一次合集名：命中 `collection-plugin-choose` = 已选，0 匹配 = 没选上。
右侧预览卡还会出现 `合集·<合集名>`（`class="info-card-text main"`），是第二重旁证。

### 坑 ㉑ 发布按钮有稳定 ref，别用坐标

`class="ce-btn bg-red"` 的 `<button>`，用 `query kind=semantic` text=`发布` 取。
注意同名的「发布笔记」侧栏入口也在匹配结果里，**要挑 `class` 含 `ce-btn bg-red` 的那个**。

坐标会随视口高度漂移（1060×1029 时在 y=984，1060×1087 时在 y=1043），
本项目 14 支里实际就撞到过一次 1043 失效、984 才准。**ref 不漂，坐标漂。**

### 坑 ㉒ 上传后别急着睡 25 秒——表单立刻就有了

> **实测范围：小红书**（`.tiptap.ProseMirror`）。抖音发布页是 `.zone-container`，
> §4.2 保留的 25 秒等待**本批未复测**，沿用旧结论——两条流程的编辑器不是一套，不要互相外推。

实测**上传完成后标题/正文字段立刻渲染**（视频还在「上传中」），不必等转码。
旧流程是「上传 → `Start-Sleep 25` → 再取 ref」，实测那 25 秒里页面可能重建，
导致刚取的 ref 全部 `STALE_ELEMENT_REF`，**已上传的视频被存成草稿**（那一支确实没发出去，
白传一遍）。

⚠️ **别把这次观察反推成「草稿箱增加 = 没发出去」**——那条推论已经被证伪（坑 ⑭）。
本坑的真正判据是**回列表核验到这条作品**，不是草稿箱计数。

**更稳的顺序**（⚠️ 不要再标注「10/10」——那是被时序运气撑起来的，见元规则二）：

```
upload_files
→ 立刻 query kind=editable 取 ref（不等）
→ fill 标题 → fill 正文（话题与正文同一次填，末段带尾随空格）
→ press_key Tab                              # 只转 span，不关面板
→ Start-Sleep 22（此时转码也完成了）
→ query kind=dom .tiptap.ProseMirror 复核正文 # 末段必须是纯文本
→ press_key PageDown（把合集按钮抬进视口上半部）
→ 选合集 → query 确认 class 变 choose
→ click .tiptap.ProseMirror p:first-of-type    # 移光标，为下一步清场
→ query kind=text .tippy-box                   # 必须 Element not found，否则不许发
→ query kind=semantic text=发布 取 ce-btn ref → click
→ 看按钮有没有转 loading                        # 没转就是被面板吞了
→ Start-Sleep 6 → query kind=text 确认表单已重置
→ 回笔记管理列表按标题核验                       # 唯一权威判据
```

⚠️ 后四步（移光标 → 查 `.tippy-box` → 点发布 → 回列表）**是 2026-10-06 补进去的**。
原版本缺了前两步，直接导致 numbers 第 04 话返工两轮（坑 ㉛）。

### 坑 ㉓ 页面重建的信号：generation 跳回 1

`navigation.generation` 是页面代号。正常递增（5 → 6 → 9 → 13…）；
**突然跳回 1 = 整个页面被重建**，此前所有 ref 全部作废，必须重新 `query`。

同时若视口在 **1060×1029** 与 **1280×720** 之间反复跳变，说明有人在同时拖浏览器面板
（见坑 ⑫）。这种情况下 `STALE_ELEMENT_REF` 会连发，重试同一动作只会继续失败——
换成 `position` 点击或干脆让出控制权。

### 坑 ㉔ 改已发布作品的正文：`fill` 会追加，全选无效，只有「End + Meta+Backspace」能清空

修 colors 第 01/09/10 话的线上缺陷时实测（2026-10-06）：

| 做法 | 结果 |
|---|---|
| `fill`（抖音正文 `.zone-container[contenteditable]`） | **追加不是覆盖**——242 字 → 364 字，`ACTION_EFFECT_MISMATCH` |
| `Meta+a` / `Control+a` + `Backspace` | 只删 **1 个字符**（话题标签间的零宽字符），全选对这个编辑器无效 |
| `End` + `Meta+Backspace` ×2 | **一次删一大段**（363 → 114 → 0），真能清空 |
| `type`（清空后逐字输入） | `verified: true`，字数精确，推荐用这个而不是 `fill` |

**能用的三步**：

```
query kind=editable → 取 .zone-container ref
→ click 聚焦 → press_key End
→ press_key Backspace modifiers=[Meta]   （×2 一般就空；没空就再来一次）
→ query kind=text 确认 N / 1000 已归零
→ type 目标全文（不是 fill）
→ query kind=semantic text=提交修改 → click
```

**两条硬约束**：

- 平台限制「**每个作品最多修改 5 次**」，超次数不可继续改。清空不干净就提交 = 浪费一次额度
  且把正文改坏。**提交前必须 `query kind=text` 核对字数与污染是否清除**。
- 改文案**不影响已有统计**（播放/完播/跳出原样保留），所以这是安全操作，不必担心数据归零。

> 与坑 ③ 是同一件事的两面：`fill` 返 `ACTION_EFFECT_MISMATCH` 之所以「属常态」，
> 正因为它压根没在覆盖——**新发布时追加无妨，改文案时就是事故**。

### 坑 ㉕ 小红书正文编辑器不认 `Tab` / `End` / `Meta+Backspace`，与抖音不是一套

抖音那套「`End` + `Meta+Backspace` 清空 → `type` 重填」在**小红书 `.tiptap.ProseMirror` 上全部失效**（2026-10-06 实测）：

| 动作 | 抖音 | 小红书 |
|---|---|---|
| `fill` | 追加 | 追加 |
| `Meta+a` / `Control+a` 全选 | 只删 1 字符 | 无效 |
| `Shift+End` 选到行尾 | 有效 | **只删 1 字符** |
| `End` 移到行尾 | 有效 | **无效**（光标原地不动） |
| `Meta+Backspace` 清空 | 一次删一大段 | **无效** |
| 单次 `Backspace` | 有效 | 有效（唯一可靠手段） |
| `type` | 有效、字数精确 | 有效，但**按段落拆成多个 `<p>`** |

**`Tab` 在小红书有两个互相独立的作用，务必分开记：**

| 作用 | 说明 |
|---|---|
| ① 不会把光标送到正文末尾 | 抖音那套「填完 `Tab` 再打话题」的流程在小红书会把话题**插进句子中间**（坑 ㉕ 的老坑） |
| ② 能把 `.suggestion` 装饰 span 转回纯文本 | 这是 `Tab` 在小红书**真正有用的地方**（坑 ②） |

于是「填完正文立刻 `Tab` 再打话题」在小红书会把话题**插进句子中间**，
还会被联想面板截断（`#多语言对比` → `#多语言` + `习`，坑 ②）。

**正确做法**：话题**作为正文的最后一段、跟着正文一次性 `type`/`fill` 进去**，
不要用 `Tab` 切焦点、不要分两次输入。输入完 `Tab` 一次（只为转纯文本），
再用 `query kind=dom selector=.tiptap.ProseMirror` 核对段落结构，确认话题落在最后一段。

⚠️ **`Tab` 之后还有一步不能省：把光标点到正文里一个不含 `#` 的段落，关掉联想面板**，
否则点发布会被面板吞掉并把候选话题写进正文。见坑 ㉛。

> 修复坏正文时的代价实测：逐字符 `Backspace` 会**连带删掉正常文字**（一次删 3 个字符、
> 误删到上一行），返工成本极高。**先验证清空手段可用，再开始填内容**——
> 这是这次的实际教训，不要在没验证的编辑器上边填边修。

### 坑 ㉖ 跳转 ≠ 入库：发布成功的凭据在列表里，不在跳转 URL 里

| 症状 | 根因 | 修法 |
|---|---|---|
| 抖音点完发布，URL 跳到 `/content/manage?enter_from=publish`、提示「发布成功」，但打开默认列表一看——**没有这支** | 默认列表把置顶的两支顶在最前，其余按旧日期排；新发布的那支不在已加载的这一屏里。**「没看到」被当成了「没有」**，于是差点向用户报一个假的失败结论 | 发布后必须用**搜索/列表条目**做判据：抖音用「搜索作品」搜标题里的稳定片段；小红书用笔记管理页搜标题。**「没看到」永远不等于「没有」**，要下「没发布」这个结论，必须先排除「没在那一屏」 |

> 这条和 §7 核验清单是同一件事的两个方向：清单管「该验什么」，
> 这条管「**什么样的观察不构成证据**」。一个跳转到管理页的 URL 证明的是
> 「流程走完了」，不是「作品入库了」——中间隔着队列、审核、可见性设置。
> 抖音那次最终是搜标题才命中的：状态**已发布**、时间 23:49、时长标 01:28。

### 坑 ㉗ 自定义封面传不上去，先分清是平台机制还是工具故障

| 平台 | 现象 | 性质 |
|---|---|---|
| 小红书 | 全页唯一的 file input 的 `accept` 就是视频格式，封面只能**从视频里截帧**，不接受上传图片 | **平台机制**。渲得再好也传不上去，不要反复试 |
| 抖音 | 316 元素的页面上 `inspect` 报 Electron 错误，`editable` 不把 file input 列为目标，`upload_files` 对两个不同 ref 都返回同一个 `Browser action failed in Electron main` | **工具能力限制**。`upload_files` 只认 `inspect`/`query` 给的 opaque ref，不接受 CSS selector |

> 处理方式是一样的：**如实说明，不要把它伪装成成功，也不要无限重试**。

### 坑 ㉙ 抖音正文的 `ACTION_EFFECT_MISMATCH` 是常态，**重试它才会出事**

抖音正文 `fill` 正常也返回 `ACTION_EFFECT_MISMATCH`——编辑器把换行存成结构化节点，
纯文本比对必然对不上（小红书是 tiptap，同样有这个错码，见坑 ③）。
**判据不是错误码，是 `effect.textLength` 是否接近预期字数 + DOM 里是不是你要的内容。**

危险在于「看到红字就重试」：填 342 字 → `textLength: 343`（正常），
发现打错一个字重填 341 字 → `textLength: 684` = 343 + 341，**两段拼在一起**，
最后一行变成「……评论区聊聊。三种语言说「我爱你」……」，直接发出去就是事故。

所以抖音正文的固定节奏是：

```
fill 一次 → 看 textLength 对不对 → 对就 press_key Tab，不再碰
```

真要重填，先按坑 ④ 清空（`Meta+a` + `Backspace`），**清完读一次 DOM**
（`query kind=dom`，selector `.zone-container[contenteditable="true"]`），
确认塌回空行，再 `fill` 正确内容，**发前再读一次 DOM 逐行核对**。

### 坑 ㉚ 站点整站 SPA 挂载失败：侧栏在、主区永远空白

**现象**：小红书创作服务平台先渲染出侧栏（`lapin`、发布笔记、笔记管理…），
主区一片空白，`query kind=text selector=body` 只剩侧栏那几十个字，随后**整页连侧栏一起变空**。
`query kind=editable` 返回 0 个目标，`query kind=semantic` 连续 `BROWSER_OPERATION_TIMEOUT`。

**已排除的原因**（别再重复试）：

| 试过的 | 结果 |
|---|---|
| `reload` | 侧栏回来，主区仍空白，几秒后整页归零 |
| `navigate` 深链 `/publish/publish` | 同上 |
| `open_tab` 开新标签页拿干净渲染进程 | 同上 |
| 换到 `/new/note-manager` 对照 | **同样空白** → 是整站问题，不是发布页独有问题 |

**诊断判据**：`query kind=text selector=body` 拿到**只有侧栏**的短文本，就说明主区没挂载，
不是「内容还没加载」。这时继续 `wait` / `inspect` / 换 selector 都是浪费——重操作还会超时。

**处理**：停手上报，让用户侧恢复（重开面板或平台侧恢复），**不要**在坏页面上反复重试，
更不要在这种状态下点发布。此时任何"发布成功"都不可信。

### 坑 ㉛ 话题联想面板不关，点「发布」会被吞掉并把候选话题写进正文

**这是 numbers 第 04 话（粤语）卡了两轮的硬阻塞，也是本手册最贵的一条坑。**

**现象**：正文末段话题已是纯文本、`.suggestion` span 已消失、DOM 逐段核验全对，
但点 `ce-btn bg-red` **发布没生效**，反而把面板里的候选项（如 `#有趣的分类`）
当成话题插进正文，**顶掉原标签前的 `#`**——原本 `#小语种` 变成「有趣的分类」。
按钮这次真的转了 loading 才是成功；没转就是被吞了。

**已排除的手段**（都别再试）：

| 试过的 | 结果 |
|---|---|
| `press_key Escape` | 无效，截图字节数完全相同 → 同一帧，面板一动没动 |
| 等 8 秒 | 无效，面板不会自动收起 |
| `hover` 到别的元素 | 无效，不是 hover 触发的 |
| 焦点移到标题框 | 无效，面板不随 blur 关闭 |
| `scroll` 页面 | 无效，面板跟着内容走，始终停在发布按钮的点击路径上 |
| 面板在 DOM 里的实际位置 | **和发布按钮并不重叠**（面板 x≈152–852，按钮 x≈1160+）——所以不是几何遮挡，是点击被面板的事件层吃掉 |

**解法（唯一奏效）：把光标点到正文里一个不含 `#` 的段落，话题查询状态立刻取消，面板消失。**

```
click selector=".tiptap.ProseMirror p:first-of-type"     # 纯文本段落，无 #，安全
query kind=text selector=".tippy-box"                     # 必须返回 Element not found
```

面板消失的判据不是截图，是 `query kind=text selector=.tippy-box` 报
`Element not found` / 返回空——`.tippy-box` 就是联想面板的容器 class。

**代价极低**：点进正文只是移动光标，不改内容。点完再 `query kind=dom` 复核一次正文，
确认没有新增节点（`ProseMirror-focused` 类会多出来，属正常）。

**正文已经被污染时的恢复法**（第 01 话验证过一遍，2026-10-06）：

误插进去的话题是 `contenteditable="false"` 的**原子节点**，可以整体删掉，
不用逐字符退格（逐字符会连带删掉正常正文，坑 ㉕）：

```
query kind=dom selector=".tiptap.ProseMirror p:last-of-type"     # 确认污染结构
click selector=".tiptap.ProseMirror a.tiptap-topic"               # 光标落到原子节点后
press_key Backspace                                                # 一次删掉整个原子节点
query kind=editable → 取正文 ref → type text="#"                    # 补回被顶替的 #
press_key Delete                                                   # 删掉夹在中间的 &nbsp;
press_key Tab                                                      # 转纯文本
query kind=dom selector=".tiptap.ProseMirror"                       # 复核
```

> 这套修复**不保证收敛**——第 04 话照着做仍不收敛，最后整支作废重做。
> 所以正确策略是**别让正文被污染**（先关面板再点发布），而不是「反正能修」。

> **流程含义**：`Tab` 之后不是「可以直接点发布了」，而是「**还差一步**」。
> `Tab` 管 span，`点非话题段落` 管面板，两步都要做。
> 02/03 之所以一次过，是因为 `Tab` 和点发布之间隔着 `ask_user` 的往返（几十秒），
> 面板在那段时间里被别的东西关掉了——**这是运气，不是流程**。别把它当成功经验继承。

### 坑 ㉜ 抖音整站卡在「加载中...」：字节浏览器校验判定 `isValidBrowser false`

**这是坑 ㉚ 的抖音变体，但形态不同，别混判**（2026-10-06 14:26 实测）：

| | 坑 ㉚（小红书） | 坑 ㉜（抖音） |
|---|---|---|
| body 文本 | 侧栏在，主区空白 | **只有「加载中...」六个字，侧栏也没有** |
| 侧栏 | 渲染出来了 | 完全没渲染 |
| 判据 | 「body 只剩短文本」 | `query kind=console` 出现 `isValidBrowser false` |

**诊断步骤**（约 2 分钟，不要多试）：

```
query kind=text selector=body              # 拿到「加载中...」
query kind=network                         # totalEntries = 0 = 主 bundle 压根没跑
query kind=console filter=isValidBrowser   # 命中 = 字节的浏览器校验把我们判为无效
→ 再开一个抖音页做对照；再开小红书做对照
```

**本批实测结论**：两个抖音页（`/publish` 与 `/content/manage`）都是同一形态、
同一 `isValidBrowser false`；同一浏览器同刻打开小红书**挂载完全正常**。
所以这是**抖音侧拒绝这个浏览器指纹**，不是本地网络、不是面板故障、也不是登录态问题。

**处理**：停手，**不要 reload / navigate / open_tab 反复试**（reload 本身会
`BROWSER_OPERATION_TIMEOUT`，只会更慢）。此时任何"发布成功"都不可信。

**恢复途径**（按代价从低到高）：等平台侧策略变化 → 用户在**正常浏览器**里打开
抖音创作者中心确认是否同样卡住（能区分「平台整体故障」与「仅内置浏览器被拦」）→
重启内置 Browser 面板换一个渲染进程。

> **排期影响**：抖音发布被卡住时**不要空等**，把该批内容转到小红书先跑，
