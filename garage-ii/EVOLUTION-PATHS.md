# 两条自我进化路径的产物对照（harness2 × RSIAgent）

> 回答一个问题：**改 harness 与改记忆，两条路径各自真的产出了什么，产物在哪、怎么验、花了多少墙钟。**
> 引擎层机制对照不在这里，见 [`../theatre-ii/COMPARISON.md`](../theatre-ii/COMPARISON.md)；harness2 自己的读数与判决见 [`BENCHMARK.md`](BENCHMARK.md)。
> 本文的每一条事实都指得出处（git 提交、行号、落盘路径）。**指不出的不写。**

## 0. 一句话结论

两条路径**产出的东西根本不是一类**：RSIAgent 改的是 `usine` 的**产品代码**（拒答卡文案 + 配套测试 + 审计文件），产物是一条 git 提交，验收是 `pnpm verify` 退出码；harness2 改的是 `usine` 的**使用方式**（喂给 dsh 智能体的系统提示与技能手册），产物是一棵 harness 树，验收是**让智能体把活真干一遍再判分**。

这个差别决定了两边的墙钟差了一个量级，也决定了「谁更管用」这句话**今天还不能说**——详见 §5。

## 3. 两条路径各自付出的「让产物出得来」的代价

这一节是本对照里最不该省略的一栏：**两条路径都不是一开跑就出产物的**，差别在于它们把时间花在了哪。

**RSIAgent 侧**（`garage/README.md` §5.1–§5.5，配合 git 提交史）：

- 2026-10-19 的 **14 次真跑里，记忆一次都没出来过**（`README.md:180`）。根因一轮一轮查出来：验证席烧穿墙钟没出版报告、guest 里根本没拿到仓库（种子在 reset 里被抹掉）、brief 没有上界导致切片吸收不了、切片计划没真正生效……对应 **10 条以上 `fix(garage): bfsN 死因` 提交**。
- 关键语义：**失败即终局的不是 FAIL，是「没有结论」**。验证席判 FAIL 也能进记忆蒸馏，验证席**没判**则什么都不出（`README.md:186`）。这一条让前 14 次的失败全部「无声」。
- DRS 深度波次是**第七次尝试**才第一次拿到 `memory_changed: true`（`README.md` §5.5，bfs16i，1650.6s / 2100s）。
- 合并侧还踩了一个只有真跑才会遇到的坑：工作树带 CRLF 而 git 认为干净，漂移闸只比原始字节 → 一条过了验证席、过了门禁的改进被判 `drift` **静默跳过**；修法是同时比折叠 CRLF→LF 的 sha（§5.7）。

**harness2 侧**（`BENCHMARK.md` §16–§18，配合本次会话）：

- 修测量层自己：判据假阳性（把「命令行里出现过浏览器」当成绕行）、臂落盘重复计数（`dom1` 臂 n=6 实为 3）、空样本被当零分、基准臂被前一次 run 的产物污染。**四条都是先量错，再改判据，旧读数作废重跑。**
- 修执行层：上下文窗口配错导致的压缩风暴（智能体的上下文被剪掉）、轨迹截断（`TRAJECTORY_MAX_CHARS` 200k 硬砍造成判据假信号）、钥匙串弹窗（真凶是本助手运行时的 headless Chrome，不是跑批；跑批侧用 `browser_shim.py` 隔离，不改被测行为）。
- 修提案通道：`/messages` 那一路每次都吐 1.1 万–2.6 万字符 reasoning，墙钟 56–116s；`/chat/completions` 不推理，36–47s。换协议后同题同树 42.1 分钟 → 18.7 分钟（步数反而更多）。
- **提案通道的两次真实失败**（`sweep-poster-fuyao-v4`，19:5x）：`inv1` 交回的是**半截文件块**（解析成「格式错误」，实际是传输截断）、`agg1` 的 183k 字符 prompt **HTTP 502**，引擎按设计回退基准树。逐条数字见 §4.4。

## 4. harness2 路径的产物：AGG 阶段合成出的那棵树

### 4.1 产物是什么

一轮 sweep（`--phase sweep --k 1`）里，引擎先跑基准 rollout（`base1`），再让两组提案分别改树（`inv1` / `dom1`），最后 **AGG 阶段**把能用的改法合成一棵候选树（`agg1`）并在这棵树下再跑一次 rollout。被采纳的树落在这里：

```
~/.cache/usine-h2-v2/sweep-poster-fuyao/adapt/usine-dsh-dsh-agg1/routing-poster/harnesses/agg1/
```

它相对基准 harness（`garage-ii/harness_base/`，14 个文件）**只多两处**：

| 改动 | 内容 |
|---|---|
| 新增一个技能 | `skills/print-poster-delivery/SKILL.md`，**4802 字节** |
| `systemprompt.md` 加一行触发句 | 第 6 行：「一页纸海报且要求「能直接打印」、或要求附「可复现的做法说明」时，加载 `print-poster-delivery`……海报工序本体仍走 `one-page-poster`」 |

`systemprompt.md` 的其余四处纪律**逐字未动**（`diff` 只报两处：插入第 6 行 + 文件末尾换行差异）。树级纪律留存轴也独立核过：5 条工作方式纪律全在、7 条红线全在，一条没改（`garage-ii/tree_discipline.py` 退出码 0）。

### 4.2 这份技能写了什么（摘要，全文在落盘路径里）

它补的是**基准 harness 的一个真空档**：`one-page-poster` 教的是排版工序，而「做成什么样才算交付」没有任何一份文件说过。新技能给的是本工作区**实测出来的门禁口径**，每条都能在 `feuille` 的命令行上验：

- **交付物是两件**：能打印的图 + 别人照着能重做的做法说明（内容清单、网格行×列、配色表、按序命令与**各自退出码**）。
- **打印尺寸**：页面 `1240×1754` 用 `feuille poster render … 1240 1754 2` 渲染出 **2480×3508 = A4@300dpi**；报「能打印」前先确认渲染输出就是这个尺寸。
- **配色 = 门禁入参**：`verify-colors` 默认按模板调色板判（red `c9403a` / blue `2f5d9e` / gray `a2967f` / ink `2c2620`）；自己配色就必须把四个 hex 原样传进去，否则门禁量的是模板色。检查是**逐格**的，所以每格都要有该色的语义层。
- **字体子集**：`fonts.json` 的 `text` 是**逐 family 的字符全集**，`audit-charset` 的家族归属是**栈式**的（镜像 CSS 继承），所以中文族里必须包含它渲染到的数字、拉丁字母与标点。
- **溢出检查**：`fit-diag` 的文本摘要**不报格子是否溢出**，要看 `?verify=1` 倒出的 DIAG JSON 里逐格 `overflowX` / `overflowY`。

**这些说法我逐条核过 `usine/` 源码，没有一条是编的**：

| 技能里的说法 | 源码里的真身 |
|---|---|
| 默认调色板 red `c9403a` / blue `2f5d9e` / gray `a2967f` / ink `2c2620`，线色 `d9cdb7` | `usine/packages/poster/src/verify_colors.ts:8`、`:28` |
| 页面 `1240×1754`，渲染倍率相乘（2× ⇒ `2480×3508`） | `usine/packages/poster/src/render_poster.ts:40-41`（默认 `1240` / `1754`）、`render_page.ts:79`（`wantW = w × scale`） |
| `audit-charset` 的家族归属是**栈式**的（镜像 CSS `font-family` 继承），无 class 的元素继承外层 family | `usine/packages/poster/src/audit_charset.ts:10-13`（几乎逐字） |

这一条值得单独说：**提案通道没有编造 API**。它引用的尺寸、色值、归属语义都能在源码里指到行——这与我原先的担心（模型会把手册里的东西「顺手写圆」）相反。

**但它有一条说错了。** 技能原文：「`fit-diag` 的文本摘要只报每个大词的 `fs` 与词框，**不报格子是否溢出**。」实际不是：`usine/packages/poster/src/fit_diag.ts:28-39` 在每一行后面打 `<-- OVERFLOW-X` / `<-- OVERFLOW-Y`，并且**任一溢出就 `return 1`**；模板也确实逐格产出这两个旗标（`usine/skills/one-page-poster/assets/template/poster_src.html:193-194`，比的是 `.word` 与 `.cell` 的矩形）。所以「要看 DIAG JSON 才知道有没有溢出」这句话不成立——CLI 已经告诉你答案了。

**这条错误的性质比它本身更值得记**：它**不会让任何判据变红**。产物判据量的是「有没有交付、有没有走工具面」，树级纪律轴量的是「纪律有没有被删」，**没有任何一条轴在量「新写进 harness 的话是不是真的」**。一份会积累错误文档的 harness，在这套判据下长得和一份正确的完全一样。

**补一句公平话**：v5 那一轮合成出的技能（`poster-print-delivery`）**没有重复这条错话**——它对 `fit-diag` 只写了「`render-page dump` 可能写出 0 字节却退出 0，先看 `fit-diag` 是否报 `no DIAG block found`」，没有声称摘要不报溢出（`harnesses/agg1/skills/poster-print-delivery/SKILL.md:36`）。所以这是**一次性错误，不是这台「蒸馏机」的稳定倾向**；但它照样说明那条轴是缺的——**两次里错一次，判据一次都没红。**

### 4.3 它被量过：Δ = 0.00，p = 1.00

**判决：这棵树是真的、被采纳的、纪律完整的进化产物；但在这套判据上它一分也没换到。** 原因不是「技能写得不好」，而是这一格的判据**被一条与演化无关的矛盾占满了**：基准 harness 自己在 `systemprompt.md:14` 禁止 shell 绕开工具面，而它自己的 `skills/one-page-poster/SKILL.md:141` 又亲手教 `google-chrome --headless --dump-dom | feuille poster fit-diag`。实测 10/10 条 rollout 都两样都干——所以 `no_tool_face_bypass` 在两臂都是 100% 失分，Δ 恒为 0。这条矛盾不是演化造出来的，是基准带进来的。

**这一段在判据两次升级后各重判过一遍，结论一字未变**：第一次是 `_cli_invokes` 修好（戳 `68cb6f1078d9`），第二次是 heredoc 修正（戳 `2c5a94416376`）。两次重判后 v4 仍是基准 `80,80,80,80`、`agg1` `80,80,80`、`dom1` `80,80,80`，逐条只失 `no_tool_face_bypass` 这一格，两次比较器输出都是 Δ = +0.00、p = 1.00、该格 100%/100%。**v4 的零格是稳的**——而 v5 那 13.3 分恰恰全落在这同一格上，两轮的差别不在演化，在判据怎么读 heredoc（§4.7）。

### 4.4 失败账（v4）与 v5（在跑，尚无读数）

`--phase sweep` 的另一次（`sweep-poster-fuyao-v5`，2026-10-20 21:09 起跑）改了一处前提：**提案者与执行器都走 `openai-completions`**。这是针对上一轮（`sweep-poster-fuyao-v4`）两次真实失败的修复，两次都在**提案通道**上、都在旧协议那条路：

| 候选 | v4 的失败 | 落盘证据 |
|---|---|---|
| `inv1` | 回复里没有可解析的文件块（`<<<FILE … >>>FILE`）——**半截文件块**，`263.2s / 2 次尝试 / 104,200 字符 prompt` | `sweep-poster-fuyao-v4/adapt/_audit/…/inv1.a1.meta.json` |
| `agg1` | **HTTP 502**（`relay: fetch failed`），`602.7s / 2 次尝试 / 183,168 字符 prompt` | 同上 `agg1.a1.meta.json` |
| `experience.agg1` | 同上 502，`602.4s / 141,673 字符` | 同上 |

AGG 拿不到合成结果 ⇒ 引擎按设计**回退基准树**，那一轮「看起来跑完了」，而最终被采纳的其实是**没改过的基准**。**产物是第一次 sweep（`sweep-poster-fuyao`）出的**——那一轮 `agg1.a1` 是成功的（`526.1s / 2 次尝试 / 193,632 字符 prompt`），只有 `inv1` 撞了 502，AGG 拿着 `dom1` 的改动合出了 §4.1 那棵树。

这一点值得再钉一次，因为「AGG 合出来的」容易被读成「AGG 想出来的」：我把四个候选逐棵树 `diff -r` 过，`dom1` **自己就已经带了**新技能（11 个技能目录）与 `systemprompt.md` 第 6 行触发句，`diff -r base dom1` 只报这两处；`agg1` 相对 `dom1` 的差别**全在技能正文的措辞**（判据/检查、五个 hex vs 四个 hex + 线色另计、`cellOver` 字段这些说法），触发句与技能文件名逐字相同。`inv1` 则与基准**逐字相同**（它那一次没交回可用改动）。所以这一轮真正提出「补交付契约这个真空档」的是 `dom1`，`agg1` 做的是合并与措辞收敛。

还有一处细节能反证「回退」这条设计是必须被看见的：`dom1`/`agg1` 的 `systemprompt.md` **末尾少了换行**（`diff` 报 `\ No newline at end of file`）。树级纪律轴不看这一条（它比的是纪律条目），产物判据也不看——所以这种「顺手把文件末字节改了」的改动，今天是**零信号**的。

### 4.5 引擎自己蒸馏的 `experience` 里，归因是错的

被采纳的树（`sweep-poster-fuyao-v5/…/harnesses/agg1/`）相对基准仍是两处：新增 `skills/poster-print-delivery/SKILL.md`（**4531 字节**），加一行触发句。技能内容比第一次那份更有据：它把本轮实测到的四个坑前置了——`verify-colors` 按颜色认网格线（格内 `.divider` 同色会被当成幽灵横线，实测 603.0）、`fit-diag` 因 `JZ Sans@700:unloaded` 退出 1、**0 字节 dump 不是 PASS**、以及 `feuille poster render` 撞 UDD 错误时的有界兜底（两次失败即停、原样报错）。

**但那行触发句是坏的。** 逐字是这样：

```

```

「当>时」不成句。我顺着它挖到两处**都在我这层**的静默缺陷，而且它们叠加才产出这句坏话：

| # | 缺陷 | 证据 |
|---|---|---|
| A | `dom1` 的表头写成 `<<<FILE context/harness/systemprompt.md>`（多一个 `>`），而 `_FILE_BLOCK` 要求 `<<<FILE\s+path\s*\n` ⇒ **整块被静静丢掉**，那一轮仍记 `ok: true`、不重试 | `dom1.a1.meta.json` 是 `ok: true, attempts: 1`；`harness.diff` 里 `systemprompt.md` 只有自动触发那一行，`dom1` 想改的第 10 行**没变** |
| B | 引擎的 `autotrigger()` 用 `^description:\s*(.+)$` 取描述首行，而 `dom1` 的技能用了 YAML 折叠块 `description: >` ⇒ `desc` 取到 `>`，我的模板 `"- 当{desc}时，加载 \`{name}\` 技能。\n"` 把它拼成了坏句 | `sweep-poster-fuyao-v5/…/harnesses/dom1/systemprompt.md` 与 `agg1/systemprompt.md` 里那句逐字如此 |

**A 的损失是真的、可复算的**：把 `dom1` 那段 `@@REPLACE` 喂给修好后的解析器，它落在 `systemprompt.md:10`，产出里含 `poster-print-delivery`——而只要它在，`autotrigger` 就会因为「名字已在 always-on 文本里」而**跳过**，B 那句坏话根本不会出现。**一处一个字符的手误，吃掉了一条要改的纪律，还顺手生成了一句坏话，而两条判据（产物 + 纪律留存）都不会红。**

修法（`garage-ii`，引擎零补丁）：

1. `_FILE_BLOCK` 表头容许尾随 `>`；新增 `unparsed_headers()` 把「像表头却没被认下」的行数出来，`call()` 一发现有漏块就**当格式错误重试**（带针对性修复指令），不再静默继续。
2. `dsh_substrate.trigger_line` 改成**不引用 `{desc}`** 的模板：`- 要做 \`{name}\` 管的那件事时，加载 \`{name}\` 技能。\n`。引擎层零补丁 ⇒ 描述首行怎么变都不会再拼出坏话；宁可通用但通顺，也不写一句「看起来带条件」的坏话。

回归断言加在 `smoke_dsh_bridge.py` 的新分组 `[12b]`（11 条，全绿）：正常表头 / 尾随 `>` 仍能解析（旧代码必挂）/ 坏表头必须被数出来 / 好块+坏表头不许只报一半 / 块内的 `<<<FILE` 示例不误判 / 折叠块描述不再拼出 `当>时`。真实的 `dom1` 回复也拿来复证过：修好后能解析出 `systemprompt.md` 并落在第 10 行。

**这两处缺陷给这一节的结论**：v5 的产物是「技能内容有用、触发句是坏的」，而坏的那半句**不是模型的错，是我这层的错**——今天第三次栽在同一类事上（前两次是读错树、按退出码量浏览器）：**判据只看产物与纪律条数，不看的正是「链路有没有把改动完整送达」和「写下来的话通不通」。**

**它走了产线，25 次。** `which feuille` 返回的就是那个 `usine-feuille-bin-…/feuille`（`usine_adapter._feuille_shim_dir()` 装的 PATH 垫片），智能体把它存进 `$FEUILLE` 再调用——完全正当的 shell 写法。而我的匹配正则 `_CLI_INVOCATION` 只认**字面** `feuille`，`$FEUILLE poster …` 与 `/…/feuille poster …` 两种写法**都不认**，于是 25 次真实调用被数成 0 次，那 0.6 分是**量错了**，不是智能体没干活。

修法与它带来的清算（都在 `garage-ii`，引擎零补丁）：

1. `_CLI_INVOCATION` 认得三种「同一个程序在位」的写法——裸词、任意路径（绝对/相对）、`$VAR` / `${VAR}`；`$VAR` 只在**本次运行里被赋成过 feuille 路径**时才算（新增 `_feuille_vars()` 扫 `VAR=…feuille…` 赋值，整条 rollout 级别生效，因为 `export` 常在一条命令里、`$FEUILLE poster` 在下一条）。
2. 判据改了就**必须重判**：`arms.py rescore` 用当前判据把两臂各 3 条轨迹重新判了一遍（不重跑模型）。基准臂从 `[60,80,80]` 变成 `[80,80,80]`，`tool_called` 失分率归 0，**Δ 从 +6.7 落到 +0.00、p 从 0.50 升到 1.00**。
3. **判据戳原本没覆盖匹配实现**，这是第二处缺陷：`usine_adapter.criteria_stamp()` 只哈希判据的 `name`/`kind`/`needle`/`weight`，我改了 `_cli_invokes` 的匹配逻辑，戳**一个字没变**（`236e4138f06a`）——于是「旧尺子量的 v4」和「新尺子量的 v5」共用一个戳，`--append` 会把两把尺子的分数拼成一条分布，而账面看不出来。已加 `_matcher_impl_digest()`：哈希 12 个决定过/不过的匹配函数源码（只去注释行，所以改注释不作废读数），戳随之变成 `68cb6f1078d9`。已实测：只加注释 → 摘要不变；改逻辑 → 变；函数被删 → 变。
4. 因为判据变了，**第一轮（v4）的读数也按纪律重判了一遍**：基准 `[80×4]`、`agg1` `[80×3]`、`dom1` `[80×3]`，逐判据仍是只有 `no_tool_face_bypass` 100% 失分——**v4 的 Δ=0.00 / p=1.00 站得住**，没有被这次改判据推翻。
5. 回归断言进 `smoke_dsh_bridge.py` 的新分组 `[12c]`（10 条，含一条真实轨迹复证）与 `[12d]`（3 条判据戳）。**验证过它有牙**：把 `_cli_invokes` 换回旧实现，`[12c]` 挂 **6 条**（绝对路径 / 同命令变量 / 跨命令变量 / 花括号变量 / `node` 形态 / 真实轨迹）。
6. **第四处缺陷：heredoc 正文被当成了被执行过的命令。** `cat > chrome-wrap.sh <<'EOF'` 之后到 `EOF` 之间的**正文**是数据，shell 从不执行它；旧判据把每一行都当命令切段，于是正文里那句 `exec "/Applications/…/Microsoft Edge" --headless --screenshot=…` 变成了「浏览器在程序位上被执行并出图」。实测影响：演化臂 r2 的 `no_tool_face_bypass` **唯一**证据就是这种正文，而 r2 真正执行的是 `CHROME_BIN=$PWD/browser.sh feuille poster render …`——**工具面自己调的浏览器，正当**。修法：`_strip_heredocs()` 在 `_shell_commands()`（唯一收口）生效，并在 `_browser_bypass_reason()` / `_cli_invokes()` / `_is_readonly()` 再剥一次作防御；`_strip_heredocs` 进了 `_MATCHER_FUNCS`，判据戳随之从 `68cb6f1078d9` 变成 `2c5a94416376`。
   这里**又踩到一个自己造的坑，值得单记**：第一版 `_strip_heredocs` 把起头行**原样保留**（`cat > x <<'EOF'`），于是它**不幂等**——第二次调用找不到终止符，会一路剥到结尾，把后面的真命令全吃掉（`cat > a <<'EOF'` 之后的所有内容消失）。既然两处收口都会剥，幂等就是前提。修法：起头行只留重定向、把 `<<'EOF'` 算子摘掉。`smoke [12e]` 12 条断言覆盖（正文含浏览器路径/含 `--screenshot`/含 `feuille poster render` 都不算；正文之后的真调用与真绕行照样看见；`--dump-dom` 仍是量；截断的 heredoc 不产出证据；**剥两次 == 剥一次**）。**验证过它有牙**：把起头行改回原样保留，`[12e]` 立刻挂一条，且失败信息直接打出 `twice="cat > a.sh <<'EOF'"`——被吃掉的内容一眼可见。

**所以 v5 到底证明了什么。** 把分数放下之后，还有两件可核的事，它们比分数更能说明这一轮发生了什么：

- **新技能真的被加载了。** 演化臂 3 条 rollout **全部** 调了 `skill({"name": "poster-print-delivery"})`（第 1 条还调了 3 次），基准臂 3 条只调了 `one-page-poster`——因为那棵树里没有这个技能。这是「那行触发句确实在起作用」的**直接证据**，不是自报。
- **产物质量没有可测差异。** 两臂 `delivered_poster_png` 与 `tool_called:usine_poster` 失分率都是 0%（各 3/3 交出成图、各 3/3 走了产线）；`mentions_page_spec` 也都是 0%。

合起来就是这一节该说的话：**进化产物是真的、它真的改变了智能体的行为，但这一批判据看不见它的好处。** 判据里有四条（技能加载、页面规格、走产线、交成图）在两臂都是满分——天花板效应；剩下一条 `no_tool_face_bypass` 是唯一有差别的格，而它**今天不可判**（见下两段）：它的读数在我的几个口径下从 p=0.20 摆动到 p=0.05（朴素实现还会给出 p=1.00）。一格天花板、一格定义未定的地板，中间没有可信的分辨力——所以**这一轮不给「提升」这个说法**。

**那唯一一条失败的判据不能读成「智能体不听话」。** `no_tool_face_bypass` 的失分证据我逐条看过，质量参差。修掉 heredoc 之后，基准臂三条仍然全部失分，而且证据是**真的**：r1 判 10 条、其中 7 条不带 `/tmp`（`--screenshot=$PWD/probe.png` 写在工作区里）、5 条带 `--screenshot`/4 条带 `--print-to-pdf`，多是用 `$CHROME` 变量执行的；r2 判 3 条（2 条在 `/tmp`、1 条在项目目录）；r3 判 13 条（12 条在 `/tmp`、1 条在项目目录）。演化臂只剩 r1 的 2 条，且**两条都在 `/tmp/fontprobe`**（`"$EDGE" … --screenshot=/tmp/fontprobe/t3.png`——真执行，但那是**探字体**，不是交付物）。判据还有一处会把变量名当程序：`_BROWSER_BIN` 是 `(chrome|chromium|edge|brave|msedge)` 的不区分大小写正则，于是 `$CHROME` / `$EDGE` 本身就能命中——这一处在这批轨迹里**恰好是对的**（同一行里 `CHROME="…Google Chrome.app/…"` 就在前面），但它是靠变量名蒙对的，不是靠解析。

**这一格今天不可判，理由是可数的**：它的判决在几个都讲得通的口径之间摆动，而摆动幅度跨过显著性门槛——

| 口径 | 基准 | 演化 | Δ | p | 性质 |
|---|---|---|---|---|---|
| 现状（带出产物开关就算「产」，含 `/tmp` 探针） | `80,80,80` | `80,100,100` | +13.33 | **0.20** | **实测**（`compare_arms`） |
| 现状 + 补上「`node` 驱动包装脚本出 PDF/PNG」这条漏判（检测器写得准，只命中演化 r3） | `80,80,80` | `100,100,80` | +13.33 | **0.20** | 按语义推——**与第 1 行同值** |
| 「产」限定为落**工作区**的产物（`/tmp` 探针算「量」） | `80,80,80` | `100,100,100` | +20.00 | **0.05** | 按语义推，需解析 `cd` 与 `$PWD` |
| 上一行的朴素实现（逐段查 `/tmp`，看不见 `cd` 设的 `$PWD`） | `80,80,80` | `80,100,100` | +13.33 | **0.20** | 实测——**退化成第 1 行** |

**同一批轨迹、同一份判据名，p 值能在 0.05 与 0.20 之间移动，而朴素实现全是 0.20。** 关键在最后两行：**「只认工作区产物」这个口径，只有把 `cd` 与 `$PWD` 解析对才实现得出来**；朴素写法（逐段查字符串）根本分不开「`cd /tmp/fontprobe` 之后用 `$PWD` 出图」和「在工作区里出图」，于是给出与现状一样的值。**一个口径的正确实现与它的朴素实现给出不同的判决——这不是我算错了，这是这个口径本身还没被定义清楚。**

**这张表我起初是手推的，实测把它推翻了一次，得记下来。** 我先写死两个结论：「只认工作区产物 ⇒ 演化臂 `[1,1,1]`、Δ=+20.00/p=0.05」和「补 `node` 漏判 ⇒ 演化臂 `[1,1,0.8]`、Δ≈+6.67/p=0.50」，然后用 `compare_arms` 真算，**两个都没算出来**：

- 「只认工作区产物」的朴素实现给出的是 `+13.33 / 0.20`（与现状同值），因为演化 r1 那两条命令是 `cd /tmp/fontprobe && … --screenshot=$PWD/t3.png`——**`/tmp` 在 `cd` 那一侧，产物路径是 `$PWD`**，逐段查字符串看不见它。要把它判成 `/tmp` 探针，得先解析 `cd` 与 `$PWD`。**「限定工作区」这件事本身就需要一个实现，而这个实现会决定读数。**
- 「补 `node` 漏判」的朴素版本更糟：它把演化 r2 一起误杀（r2 只用 `node build.mjs` 生成 HTML、**没有**驱动浏览器），于是演化臂变成 `[0.8,0.8,0.8]`、Δ=0.00、**p=1.00**。**想抓一条真实绕行，先误伤了三条正常构建，把结论从「有差别」打成「完全一样」。** 而写得准的检测器（只命中 r3）算出来是 `+13.33 / 0.20`——与现状同值，也就是说**这条补丁修的是正确性，不是判决。**

净结果：**四个口径里三个给 p=0.20，只有一个（需要额外实现的「只认工作区」）给 p=0.05。** 判决悬在一个实现细节上。

**这三种口径我一种都没有采纳为结论**，理由分两种：收紧到「只认工作区产物」会让 Δ 变大且显著（基准臂在工作区里出 `probe.png`、演化臂只在 `/tmp` 探字体），那是我调尺子去凑一个想要的结论；而补 `node` 漏判修的是另一个方向的缺陷（它会让演化 r3 失分），不修则尺子对**真实绕行**视而不见——但我试写的版本先误伤了正常构建，说明**这条补丁本身也需要被验证**。两个方向都有据、且都有实现风险，所以**这一格的正确定位是「待重造」，不是「已量到」。** 重造时该按纪律原文（`systemprompt.md:14`「绕开工具面做出来的东西」）把「探针」与「交付物」分开定义，并拿**交付物本身的来源**（成图是不是 `feuille poster render` 写的）来判，而不是数浏览器被调用了几次。

（顺带记一条**幸存的漏判**，已核实但未修：演化 r3 有 `CHROME_BIN="$PWD/chromium-wrapper.sh" node print.mjs`，产出 `poster-a4.pdf` / `poster-300dpi.png`；判据完全没看见，因为程序位是 `node`。同一批里 `CHROME_BIN="$PWD/chromium-wrapper.sh" feuille poster render …` 是**正当**用法——`CHROME_BIN` 本来就是让工具面指定浏览器的开关，包装脚本只是补 `--user-data-dir`；判据对这条判对了，不能因为「路径里带 chromium」就翻案。）

**我修了它的一半，没修另一半，这条界线是这么划的。** 修的是**语义上无争议**的那一半：heredoc 正文是数据、不是命令，shell 从不执行它——把正文当成执行证据是**纯错误**，无论结论往哪边倒都该改（第 6 条）。没修的是**需要定义**的那一半：「带出图开关的 `/tmp` 探针算不算产」。这一半无论往哪边定都有据，而往「只认工作区产物」定会让演化臂过关、Δ 变显著——**那等于我调尺子去凑一个想要的结果**，所以它保持明写的未决项。

**这里要钉一条比结论更重要的纪律**：「修判据」与「调尺子」的分界不是「改了还是没改」，而是**改动是否有独立于结论的理由**。「正文不是命令」有（shell 语义），「探针不是产」没有（取决于你要判什么）。前者改完读数从 0.00 变 +13.33，我说它该改；后者按语义推会让读数从 +13.33 变 +20.00 且显著，我说它不该由我来定。**同一个动作，一个算修错，一个算凑数，区别只在理由，不在效果。**

最后一件必须说清的事：**「被采纳」不是「比出来的」**。v5 的 `selection.json` 里 `why` 写的是 `trivial pool: single final at k=1; delivered without a selector session`——`k=1` 时最终池里只有一个候选，选树**没有经过任何评分比较**（`chosen_is_base: false` 只表示「不是基准树」，不表示「分数更高」）。所以这一轮的「采纳」是流程产物，不是质量结论；把它读成「引擎 judge 认为 agg1 更好」会高估它。



## 5. 诚实账：今天能说什么，不能说什么

### 5.1 能说的

1. **RSIAgent 路径真的产出了东西，而且进了仓库。** 三条合并提交可以逐字复查（`git show eedaf73` / `1d550b2` / `6e8665f`），改动是一句一句的拒答卡改写加配套测试钉子，门禁 `pnpm verify` 三次都是 exit 0、24.7–26.4s。

## 6. 与共识的偏差（这轮踩到、值得记一笔）

- `compare_rsiagent.py` 原先只在 `adapt/` 布局里找被选中的树，而实跑走的是 `sweep` 布局：h2 臂会**静默退化成基线**，报告上看起来「h2 与 base 一样」。已修（两种布局都认，并新增 `--h2-tree` 显式指定）。
- 同一份文档里那句「RSIAgent 的波次至今没跑完过一次」是 10-20 早上之前的事实，**当天就不再成立**。已按可取证的三条提交改正——旧断言留在文档里，比没有文档更坏。
- **「被采纳」不等于「AGG 想出来的」**：这一轮真正提出改动的是 `dom1`，`agg1` 只做了合并与措辞收敛（§4.4 末）。把 `chosen_label` 读成「功劳归属」会高估最后一个阶段。
- **数产物时先确认尺子量的是谁**：我第一次按 `job/settled` 的 `exit code` 数浏览器成败，数出「`dom1` 裸浏览器 5/5 全成功」——因为命令尾部 `; echo "exit=$?"` 把 Chrome 的失败吞了（§4.5 末）。**方向恰好反了，差一点就写成结论。**
- **产物判据管不到「写下来的话是否属实」**：技能里一条错话（§4.2）与 `experience` 里一条错归因（§4.5）都是零信号——两条判据轴（产物、纪律留存）都不量文本真假，而后者会被下一轮继承。
- **链路没送达 = 改动凭空消失，而且账面是绿的**：表头多一个 `>` 就让一个文件块被静静丢掉，那一轮仍记 `ok: true`（§4.6 A）。**凡是「解析 → 应用 → 落盘」的路径，必须有一条「用户意图的数量」对账**（几个块进来、几个落地、几个被丢），只看最终文件长得对不对是查不出来的。
- **兜底模板不许依赖上游字段的形状**：自动触发句原本引用 `{desc}`，而上游取的是 frontmatter 描述首行——对方一用 YAML 折叠块，兜底句就变成「当>时」（§4.6 B）。**兜底路径要假设上游会给任何形状**，否则修机制的那条路自己会造缺陷。
- **判据认「程序」还是认「拼写」**：`$FEUILLE poster render …`、`/…/usine-feuille-bin-xxx/feuille poster render …`、`node …/feuille.js poster render …` 三种写法都是**同一个 CLI 在位**，而我的正则只认字面 `feuille`——于是 25 次真实调用被数成 0 次，造出一个 **Δ=+6.7 / p=0.50** 的假提升（§4.7）。纪律原文管的是「绕开工具面」，不是「必须把可执行名写成裸词」。**判据要比的是行为，不是拼法。**
- **判据戳必须覆盖匹配实现，否则两把尺子的分数会共用一个戳**：`criteria_stamp` 只哈希 `name`/`kind`/`needle`/`weight`，改匹配逻辑戳不变（`236e4138f06a` 前后相同），`--append` 会把新旧判据量出来的分布拼成一条而账面看不出来。已加匹配函数源码摘要（只去注释行），戳从 `236e4138f06a` → `68cb6f1078d9` → `2c5a94416376`（后面这次是 heredoc 修正带进来的，§4.7 第 6 条）。**「同一把尺子」这句话得由代码证明，不能由注释声称。**
- **回归断言要证明「旧代码会挂」**：`[12c]` 的 10 条断言里，把 `_cli_invokes` 换回旧实现会挂 6 条——**不能挂的断言只是装饰**。同一批还牵出 `node …/feuille.js` 那条旧代码本来就坏，一直没人用那种写法所以没暴露。
- **别为了让结果好看去动尺子**：`no_tool_face_bypass` 若按「产物必须落在工作区才算产」收紧，基准臂（工作区里出 `probe.png`）会失分、演化臂（只在 `/tmp` 探字体）会过关，**按语义推 Δ 会从 +13.33 变成 +20.00、p 从 0.20 变成 0.05**——也就是从「不显著」变成「显著」（这个值需要先解析 `cd` 与 `$PWD` 才实现得出来，朴素写法给出的是与现状相同的 +13.33，见 §4.7 的表注）。我没有那么改——把「探针算不算产」留成明写的未决项（§4.7）。**尺子一动，读数就先验地向有利于改动者的方向漂。**
- **「修判据」与「调尺子」的分界是理由，不是效果**：同一个文件、同一批轨迹，我把「heredoc 正文不是命令」当错来修（shell 语义上有独立依据），把「探针不是产」留成未决项（无论往哪边定都有据）。前者让读数从 Δ=0.00 变 +13.33，后者能让它变 +20.00 且显著——**判断依据是「改动有没有独立于结论的理由」，不是「改完读数变好还是变坏」**。两条都按这个标准做，才不会变成「有利于演化就改、不利于演化就不改」。
- **heredoc 正文不是命令**：`cat > wrap.sh <<'EOF'` 到 `EOF` 之间是**数据**，shell 从不执行它。旧判据逐行切段，于是正文里那句 `exec <浏览器> --screenshot …` 成了「浏览器在程序位上被执行并出图」，演化臂 r2 的唯一失分证据就是这么来的。**凡是「把一段文本当命令读」的地方，先问它到底会不会被 shell 执行。**
- **剥块函数必须幂等**：修 heredoc 的第一版把起头行原样保留（`cat > x <<'EOF'`），于是第二次剥就找不到终止符、一路剥到结尾，把后面所有真命令吃掉（实测 `twice="cat > a.sh <<'EOF'"`）。**两个收口都会调用的清洗函数，幂等不是优点而是前提**；断言要直接比 `f(f(x)) == f(x)`，别只比「剥一次对不对」。
