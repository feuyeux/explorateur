# 平台能力边界与实测结论

> 只记**本skill 实跑验证过**的结论。每条都注明验证方式与日期。
> 手册（`docs/reference.md` §5）记的是跨项目通用流程；
> 本文记的是**多语种 + 横竖双版**这个具体形态下新测出来的东西。

## 1. 双版式分发：竖版 → 抖音，横版 → B站

《四季》项目的选型依据（2026-10-08，用户拍板）：

| 平台 | 版式 | 依据 |
|---|---|---|
| 抖音 | 竖版 720×1280 | 信息流吃竖屏；封面 3:4 与项目 1080×1440 原生一致，零裁切 |
| B站 | 横版 1280×720 | B 站是横屏观感，竖版浪费两侧 |

**不要默认「同一批素材发同一版式」。** 双版式项目分发时按平台的
主要消费形态选，封面原生比例能对齐就不要再裁。

## 2. B站合集：Lv2 门槛，**做不到就是做不到**

@feuille/publish `collections` 头注已记录：合集需创作中心 Lv2，
等级不够时编辑页是灰字、无可点控件，合集管理页 404 或重定向。
`collections.py` 里**只有抖音实现了全流程**（`fix_collection` /
`create_collection` 都是抖音 URL）。

**处置**：本批 B 站 12 条**裸投稿、不建集**，如实告诉用户合集等升级后再补挂。

> 这条的教训不是「B站没有合集」，而是：
> **能力边界要在承诺之前查清，而不是发到一半才发现。**
> 承诺了做不到的事，代价由用户承担。

## 2b. ⚠️⚠️ 抖音合集「挂不进去」的三层原因（2026-10-08 实测，逐层剥）

**现象**：`create_collection(want=12)` 报「面板无未添加行，待加=0」，
四次重搜全是空。但**截图明明白白有作品、每行右侧都有「+」按钮，完全可点**。

按手册坑 1.2 的说法，这像是「作品面板被服务端错误清空」。**但不是。**
根因是选择器里三处**硬编码实测值**：

| # | 硬编码 | 实际 | 后果 |
|---|---|---|---|
| ① | `r.x < 1500 \|\| r.x > 1600`（JS_PLUS） | viewport=1700 时「+」在 **x≈1674** | **全部候选被过滤** → 报「没有未添加的行」 |
| ② | 行文本必须 `includes(search_kw)`，传 `"四季"` | 12 条标题里**只有 3 条**含「四季」 | 9 条**静默漏挂** |
| ③ | `JS_PANEL_EMPTY` 把「没有更多视频」当故障 | 那是**分页到底**的正常文案 | 把正常状态误判为异常 |

**修法**：① 改为**相对视口**判定（`r.x + 24 < vw * 0.62` 排除 → `r.x > vw - 14` 命中）；
② 去掉文本过滤，「未添加的一律返回」，数量核对交给调用方；
③ 判据改成「共 0 个作品」或服务端错误。

**同时**把 `JS_COUNT` 从二态改成**三态**——原来空合集时页面根本没有
「合集内作品 N」这段文本（只有标题 +「点击添加作品」），
正则匹配不到返回 **-1**，与「面板被清空」混为一谈。现在：
正数 = 计数 / 0 = 确认空 / -1 = 未知。

> **教训（比修法重要）**：
> 「面板空了 → 平台故障」是一个**过早的结论**。先去看截图。
> 本项目里平台一直是好的，错的是选择器——
> 而且是那种「自己量了一次、写成常量、再也不复核」的量。
>
> 硬编码的几何量（x 坐标、尺寸、视口宽）**必然会在另一个项目失效**，
> 而且失效方式是**静默的**：不报错，只是返回空结果。
> 凡是把实测值写进选择器的地方，都要问一句「换台机器还成立吗」。

## 2c. ⚠️ 同一份几何判据写了两遍 → 修好一处漏一处

上一条修完 `JS_PLUS` 后，挂入数从 **0 → 9**（12 次点击）。但**离 12 还差 3**，
且日志显示轮 10/11/12 **加的是同一条希伯来语**，连点三次。

**根因**：`_add_loop` 里为了「滚动进视口再取新鲜坐标」**另有一段 JS**，
里面**又抄了一遍** `r.x > 1500`。两处硬编码，修了 `JS_PLUS` 却漏了这段——
滚动永远找不到元素 → 拿旧坐标 → 点到同一行。

**修法（两条都要）**：

1. 两处几何判据**统一成相对视口**的同一份写法
2. **加去重护栏**：按行首文字 `seen` 集合，已点过的直接跳过；
   连续 6 次取到同一支就判定「定位失效」并停止

**为什么第 2 条比第 1 条更重要**：第 1 条治的是这次的病因，
第 2 条治的是**这类病的家族**——任何「循环点 N 次」的批量操作，
一旦坐标或定位逻辑失效，**重复点击会伪造出一个看起来合理的计数**。
12 次点击 → 计数 9，而日志里 `added.append` 记了 12 条。

> **计数必须按「不同的东西」数，不是按「操作次数」数。**
> 批量 UI 操作里，这是最容易被自己骗过去的地方。

> 另外注意：**同一处逻辑抄两遍几乎必然漂移**。修的时候要 `grep` 全文件，
> 不是只修你看到的那一处。

## 2d. ⚠️⚠️ 封面补传「定位器写死了上一个项目的标题格式」

**现象**：`fix_covers(--only 1)` 报「页面有 3 个「编辑作品」按钮、**0 个标题**」，
整条卡在「没找到那条」。

**根因**：`douyin.fix_one` 的标题定位器写死成

```python
titles = page.get_by_text(f"「{search_kw}」的", exact=False)
```

即「**「X」的Y版**」这种标题格式——那是**上一个项目**的文案格式。
本项目标题是「老树枯枝立野原，中文的冬天很轻」，**不含该结构** → 匹配 0 个。

**与 §2b 是同一类病**：**把某个项目的文案格式/坐标当成通用格式**。

**修法**：直接用**清单里的真实标题**做前缀匹配，与文案格式解耦：

```python
rows = [(i, eds.nth(i).locator("xpath=../..").inner_text()) for i in range(eds.count())]
idx = next((i for i, t in rows if want[:10] in t), None)
```

### ⚠️ 但这个修复引入了更严重的问题（未完成，请勿照抄）

改成「全页定位退化分支」后（`all_titles.nth(j)` 与 `eds.nth(j)` **按下标对齐**），
第 1 次验证把**中文的封面盖到了韩语的作品上**——编辑页截图里标题是
「가을이 깊이 오니」，而脚本自报 `✅ [01] 中文`。

**根因**：两条作品在页面上的**下标不一致**（标题元素与编辑按钮属于不同容器树，
各自 `nth()` 的枚举顺序不能保证对应）。「同一下标」是个**看起来无害的假设**。

> **教训（下一次从这里接着做）**：
> **批量 UI 操作里，「元素 A 的第 i 个 == 元素 B 的第 i 个」是默认假设，
> 而这个假设通常不成立。** 必须用**可观测的关联**（共同祖先容器、
> `data-*` 属性、同一行的文本），而不是靠下标对齐。
>
> 另一个更硬的规矩：**补封面 / 改文案这类「修改已有作品」的操作，
> 在编辑页必须回读标题并与清单逐字比对，不一致就中止**——
> 改错对象比没改更糟，因为它消耗修改额度（抖音上限 5 次/作品）
> **而且看起来是成功的**。

## 2e.⚠️ 同一批作品里，旧项目与新项目可能同名冲突

面板里能看到 **2026-10-06 发布的旧作品**（时长 00:15，标注「已加入其它合集」）。
合集面板「共 60 个作品」里混着历史批次。

**影响**：
- 用标题关键词搜索会**搜到旧作品**，从而加错对象；
- 已在其它合集里的作品**不能重复加入**，点击静默无效——
  脚本会以为「点过了」，实际计数不变。

**判据**：进面板后先看**发布日期**，只有本批日期的作品才是目标。
不要只看标题像不像。

## 2f. ⚠️⚠️ 核验「列表页」本身不可靠——必须用服务端过滤

**现象**：同一批稿件，两次核验分别报「缺中文+日语」和「缺中文+德语」，
但稿件时间戳是**连续**的（说明都在）。页面文本长度两次都是 11745 字。

**根因**：稿件管理页是**懒加载 + 分页**。靠滚屏读全文会漏——
读到的边界在飘，**两次漏的不是同几条**。

**更严重的后果**：漏读会被当成「没发出去」，
从而触发**重发已经发过的稿件**，产生真的重复作品。

**修法**：用**搜索框**逐条核验。搜索是**服务端过滤**，
输入标题片段只返回匹配项，不依赖客户端渲染完整：

```python
box = page.locator("input[placeholder*='搜索稿件']").first
for t in tasks:
    box.fill(norm(t["title"])[:6]); box.press("Enter")
    hit = norm(t["title"])[:6] in norm(page.inner_text("body"))
```

实测：**滚屏报 10/12，搜索报 12/12**——后者是对的。

> **教训（这条比前面所有条目都重要）**：
> **核验工具自己也会有假阴性。**
> 前面几条讲的是「怎么让核验工具别骗自己」，这一条是
> **「先确认核验工具本身可信，再去相信它的结论」**。
>
> 识别方法很简单：**同一份数据，两次跑出不同的缺失名单，
> 而数据没变——这就是工具不可信，不是数据有问题。**
> 数字对不上时，先怀疑判据。

### 2f.2 比对前必须归一化（码位归一会造成假阴性）

阿拉伯语标题 `قَحْطَلَت` 的前几个字母全是 harakat 元音符号，
抖音存储时会做**码位归一**（`قَحْطَلَ` → `قَحطَل`），
逐字 `in` 判定必然失败。

```python
def norm(s):
    return "".join(
        c for c in unicodedata.normalize("NFD", s)
        if not unicodedata.combining(c)
        and unicodedata.category(c).startswith(("L", "N"))
    ).lower()
```

实测：归一化前报「阿拉伯语未发布」，归一化后 12/12 全中。
**假阴性的危害和假阳性一样大**——都会导致重发或漏改。

## 3. 封面在抖音是「发布后补」，不是「发布时设」

`douyin.publish_one` 走的是两步法：发布时**不设封面**，发布后用
`fix_covers` 走编辑流程补。原因写在脚本输出里：`upload_files` 的工具限制，
发布表单的封面面板喂不准。

手册 §0 的能力边界（坑㉗）也记了同一件事：自定义封面**传不上去**，
小红书只能截帧、抖音是工具限制。

**所以「带封面」的真实含义是**：发布后用 `fix_covers` 补上，
**并回作品管理列表确认缩略图里有文字**才算数。

⚠️ **修改额度是硬约束**：抖音每作品**最多改 5 次**，补封面算 1 次。
`fix_covers` 的 `only` 参数就是为这个设计的——**先只补 1 条验证落库**，
确认缩略图真出文字，再批量。不要在没验证的路径上一次烧 12 次额度。

## 4. 素材命名：三套体系并存，猜错必被闸门拦下

`build_manifest` 的素材存在性前置校验会在**发布前**把猜错的路径全批拦下。
这次实测踩到两个坑，都被它当场抓住：

| 坑 | 我以为的 | 实际 |
|---|---|---|
| 成片命名 | `竖版四季_ru-RU.mp4`（locale） | `竖版四季_俄语.mp4`（**中文语种名**） |
| 封面序号 | 每个版式各自从 01 开始 | **全局连续**：横版 01–12、竖版 13–24 |

**规则：`ls` 看真实命名，再写映射。** 这道闸门是盟友不是障碍——
它把「发到一半才发现文件不存在」变成「一开始就报」。

## 5. 抖音正文末尾必须留尾随空格

`#话题` 在 blur 时会被 Slate 识别成话题候选并弹联想面板，**选中无关联想词**，
导致 `fill` 的插入语义把原文重复追加。

⚠️ 已造成线上事故：第 01 支英语发出时 242 字，正确版本只有 124 字。

**解法**：正文最后一个标签后**留一个尾随空格**，话题保持纯文本。
抖音、小红书都适用。

## 6. 判据：草稿箱计数是**假判据**

小红书在**编辑过程中就自动存草稿**，发布成功后**草稿不清理**。
实测四支全部发布成功，草稿箱却单调上涨 (1)→(3)→(4)。

**照草稿箱判会把成功报成失败 → 触发重发 → 产生真的重复作品。**

唯一权威判据：**回作品管理列表核验到这条作品**。

## 7. CLI 路由表会说谎（本 skill 顺手修掉的一个真缺陷）

`feuille/cli.py` 的文档字符串曾宣称有 `cover make`、`framehash save`、
`audit run`、`metrics analyze` 等 8 个子命令，但 `COMMANDS` 路由表里
**一个都没有**——`feuille cover make` 静默返回「未知命令」。

而 `scripts/verify_cli.py` 只机检「已登记的叶子可达」，
**不机检「文档宣称 ⊆ 已登记」**，所以它一直没被抓出来。
（TS 时代：对应机检在 `packages/cli` 的 router/cli 测试——登记叶子可达 + 路由表契约。）

已修：补齐 `cover`/`manifest`/`publish` 路由，并给 `verify_cli.py` 加上
反向机检。**8/8 PASS**。

> 教训：机检的方向很重要。只查「登记的能跑」查不出「宣称的是假的」——
> 这跟发布侧「草稿箱计数查不出真成功」是同一类错误：
> **验证了 A，就以为 B 也被验证了。**

# 双版式项目特有的四个坑（2026-10-08 实测）

这四条都是「一份素材两个版式发两个平台」才出现的，单版式项目碰不到。

## 8.⚠️ 文案正文被文件尾部污染（已造成线上事故）

**现象**：12 条里**最后一条**（韩语）的话题从 6 个变成 **25 个**，
正文多出整个文件尾部的汇总表格。

**根因**：文案解析器只认 `## N · 语言` 作节的起止，但文件尾部还有
`## 附：可以直接抄的标签池`（二级标题，但不是节标题）和
`## 附：24 条对应关系`。解析器一路吞到文末，把标签池里 19 个标签
当成了韩语那条的话题。

**修法**：

```
封口条件 = 任何标题行（#{1,3}）都封口，不只是同级节标题
```

**教训**：**最后一节永远是解析 bug 的高发区**——只有它后面没有下一个
同类节标题来触发封口。测解析器时**必须单独看最后一条**，
它和前 11 条的行为不一样。

## 9. ⚠️ 横竖两版文案同名，dict 互相覆盖

**现象**：两个平台拿到的都是**竖版**文案，但抖音投竖版、B 站投横版——
文案与成片对不上。

**根因**：文案里横竖两版各有 12 节、**语种名完全相同**。
按语种存 dict 时，后一版覆盖前一版。

**修法**：**键必须带版式**——`{(版式, 语种): {...}}`，
每个平台取**与成片同版式**的文案。

> 更一般的教训：**任何"多维度分组后存 dict"的结构，
> 都要先确认每一维的组合键唯一。** 只用其中一个维度当键 =静默覆盖。

## 10. ⚠️ B 站封面必须单独出 4:3，不能靠平台裁

**现象**：把 3:4（1080×1440）封面交给 B 站，它按 4:3 居中裁切后
**标题整块消失**——只剩顶部一个「中文·春」标签。

**根因**：封面文字是**底部锚定**的，4:3 裁切窗口（810px 高）落在上半部。

**实测**：模拟裁切后逐帧看，确认底部文字一块不剩。

**修法**：给 B 站**单独出一版 4:3**（1080×810），文字块改
**横向一行**排布（`季名 ── 标题`），而不是底部竖向堆叠——
4:3 只有 1080px 宽，窄版式会让长标题折 3 行挤爆高度。

`封面.py --bili` 就是这个实现（源文件归档在 `multilingual-video-poetry` skill 的
`assets/example/` 下——封面归它，本 skill 只管投递）。

> 通用判据：**投给平台的图，先按那个平台的原生比例模拟裁切一遍，
> 看文字在不在安全区内**。能零裁切就零裁切，别指望平台替你裁。

## 11. ⚠️ Edge headless 视口亏空会吃掉底部文字

**现象**：4:3 封面渲染出来**尺寸对**（1080×810）但底部标题被切掉。

**根因**：`edge_screenshot` 的窗口高度 = `canvas_h + 视口亏空`
（macOS headless Edge 实测亏空 **84px**，与 canvas_h 无关），
截图后再裁回 `canvas_h`。

HTML 里 `bottom:56px` 是相对**视口**（894px）算的，元素被压到
810px 画布**外** 84px 处，裁完正好切掉。

**修法**：底部偏移要**加上亏空量**：

```python
deficit, _ = textlayer.viewport_deficit(1440)   # 探一次，缓存
bottom_px = BOTTOM + deficit
```

3:4 那版没暴露这个问题，是因为字号大、底部留白厚，84px 仍在安全区内。
**矮画布（4:3）比高画布（3:4）更容易踩到。**

## 12. ⚠️「存草稿」模式的平台机制（2026-11-03 实测，两平台各不相同）

存草稿 ≠ 发布，但**落库判据**同样不能靠脚本自报。两平台的真机制差得很远，
照「点完就算」写，存进去的是**残片**或**压根没存**。

### 12.1 抖音：键是「暂存离开」，落库信号是**横幅**

| 项 | 实测结论 |
|---|---|
| 草稿键 | 「**暂存离开**」（投稿页可见按钮里没有「存草稿」/「保存草稿」） |
| 落库信号 | 上传页顶部横幅「**你还有上次未发布的视频，是否继续编辑？**」 |

### 12.2 B站：键是 `<span class="submit-draft">`，落库信号是**URL 落地**

| 项 | 实测结论 |
|---|---|
| 草稿键 | `<span class="submit-draft">存草稿</span>`——**不是 button/div** |
| 点击后 | `POST /x/vupre/web/draft/add` ⇒ 页面跳到 `/platform/upload-manager/article?group=draft`（草稿箱） |
| 成功 toast | **没有**。页面上只有两行 tips：「部分草稿可能会过期，仅保存部分字段 草稿箱最多保存30个稿件」「暂不保存：卡片配置、章节配置等信息」 |
| 落库判据 | **URL 落地**（`upload-manager`）——文案判据在 B站是猜的、实测不成立 |

**坑**：

1. **别用「按钮清单」判断某个平台上有没有草稿键。** 诊断用的清单只查
   `button,[role=button],.semi-button,.bcc-button,a`，而真键是 **span** ⇒
   清单里压根没有它 ⇒ 看着像「这平台没有草稿键」。
   要判就查 DOM：`span.submit-draft` 的 `cursor` 是浏览器算出来的 `pointer`
   （tag 是 span、role 空、class `submit-draft` 不含 `button`/`btn`
   ⇒ 结构路全不命中 ⇒ 靠 class 猜「可点」会把它误杀）。
2. **草稿里封面在，卡片/章节配置不在。** tips 明说「暂不保存：卡片配置、章节配置等信息」

   （B站与抖音不同，别把抖音「草稿态给不了封面」的结论套到 B站上）。
   抖音的封面仍按既有纪律**发布后补**。
3. **创作声明只有 1 个 select、13 个选项**，「内容为自制：未经作者允许，禁止转载」
   是**其中一个选项**（不是独立字段）。
   ⚠️ 展开后要读**完整选项列表**（`ul.bcc-select-option-list`），
   扫视口可见文本会**漏掉列表末尾的「自制」**（实测只读到 6 项）。
   同理：选项匹配要**精确文本**（子串会让「内容为」命中「内容为转载」），
   且**只选一个值**（同一个 input 被后写覆盖 ⇒ 必填框值被冲掉）。

4. ⚠️ **封面判据不能一次采样，要「等」**（2026-11-03 10:52 条 3 被误杀）。
   「封面制作」弹窗**没关**的时候，主表单的封面位就还是「添加封面」空块——
   弹窗只是**盖在它上面**，空块自己有盒子 ⇒ Playwright 判它 visible。
   ⇒ 一次采样必然在弹窗关闭前报「封面未生效」⇒ 中止本条，
   而同一时刻的截图里**封面明明已经设上了**（是判据的时序问题，不是封面没生效）。
   ⇒ 判据改成轮询等两件事同时成立：① 封面位不再是空块 ②「封面制作」弹窗已关。
   ⚠️ 顺带：封面弹窗里 AI 生成封面在跑时，底部按钮文案是「**制作中…**」；
   这时候满页找「完成」会**误点别的**「完成」⇒ 弹窗关不掉。
   ⇒ 只在封面弹窗**内部**找可点的确认键（`cursor:pointer` 且不是禁用态）。

5. ⚠️ **「标题框出现」≠「视频传完」**。编辑表单在传的过程中就能填，
   实测条 3（256.4MB）的封面步骤时视频区还显示
   「已上传：256.4MB/256.4MB 当前速度：3.6MB/s 剩余时间：>1天」——
   字节满了但平台没切到「上传完成」态。
   半成品的素材进草稿 = 抖音那条「转码完成是假绿灯」的同一个坑
   ⇒ 封面与存草稿之前先等平台自己显示「上传完成」，等不到就**中止本条**。
## 13. ⚠️ B站「定时发布」控件（2026-11-15 实测，DOM 探针）

**为什么单列一节**：日更产线要在稿件里**预置**「定时发布」时刻（配合「只存草稿」＝人工点投稿才生效），而这个控件是 B站投稿页里**最容易静默失效**的一个：选不中不会报错，只会让稿件**按默认时刻发出去**。

### 13.1 控件形态

| 环节 | 实测选择器 / 结构 | 备注 |
|---|---|---|
| 开关 | `div.time-switch-wrp > div.switch-container` | **自绘开关**（`span.switch-roll` 是滑块）——**不是** `input[type=checkbox]`；打开后 class 变 `switch-container-active` |
| 开关容器 | `div.time-container` | 页面里有**两个**（一个可见、一个隐藏副本）⇒ 选择器必须**按可见性**筛，不能用 Playwright 的唯一性匹配 |
| 时刻区 | `div.time-picker > div.d-time-container` | 点开开关才出现 |
| 时区 | `div.date-picker-timezone-wrp > div.bcc-select` | 默认 `(UTC+08:00) Beijing, Chongqing, Hong Kong SAR, Urumqi` ⇒ 填 09:00 就是北京时间 09:00 |
| 日期显示 | `div.date-picker-date p.date-show` | 文本形如 `2026-11-15`，点它开日历面板 |
| 时间显示 | `div.date-picker-timer p.date-show` | 文本形如 `19:12`，点它开时分面板 |
| 日历面板 | `div.date-picker-container` | 月份标题 `p.date-picker-nav-title`（`2026年11月`）；日期格 `div.date-picker-body-item.date-item`（**过去的日子**带 `date-item-disabled`）；翻页箭头是 `div.date-picker-nav-wrp` 里的 4 个 `svg`（左 2 右 2） |
| 时分面板 | `div.time-picker-container` | 两列 `div.time-picker-panel-select-wrp`：第一列 24 个**小时**格、第二列 12 个**分钟**格；格子是 `span.time-picker-panel-select-item`（**不是 div**） |

### 13.2 三条硬约束（不按这三条写就会静默选不中）

1. **禁用态跟当前时刻绑定**：没选日期时，早于当前小时的格子带 `time-select-disabled`，**点了没反应**。⇒ 必须**先选日期**；选完「明天」后 24 个小时格才全部解禁。
2. **点小时不带分钟**：点完小时 `09`，分钟仍保留原值（显示 `09:12`）——分钟要**另点**一次。
3. **分钟步长 5 分钟**：可选值只有 `00/05/…/55`；不是 5 的倍数的分钟点不中。

### 13.3 平台侧约束（页面自己写的）

- 可选范围：**最早 ≥5 分钟、最晚 ≤15 天**（「花火、预约、互动视频稿件不可修改/取消」）。
- ⇒ 「今天 09:00 跑批」能预置的最早时刻是**次日 09:00**；定时发布时刻早于当前时间会被拒。

### 13.4 分区只有一级（2026-11-15 实测）

分区是一个 select，**30 个主分区**（影视 / 娱乐 / 音乐 / … / 知识 / 人工智能 / 科技数码 / …）；显式选中「知识」之后**不会**出现二级子分区控件，页面里也搜不到「科学科普」「子分区」字样。⇒ **子分区是投稿确认那一步的事**，草稿态只带一级分区；写文案时说「知识区 · 科学科普」时，人工点投稿时仍需在确认弹窗里选二级。

### 13.5 ⚠️ 风控会伪装成「标题没录进去」（实测踩到）

上传后弹**短信验证**「请完成短信验证」（验证码发到该账号注册手机号），弹层是 `div.base-verify risk-captcha sms-verify` + `div.base-verify-bg`，**盖住整个表单** ⇒ 标题框 `click` 被拦截、Playwright 反复 retry ⇒ 最终报「标题没录进去 → 中止」。

- 真因是风控，不是标题框坏。⇒ **填标题之前先判风控**，命中就**只等不代填**（纪律 21），等人工过完验证再确认遮罩真的没了。
- 判据词：`请完成短信验证` / `请完成验证` / `短信验证` / `获取验证码`。
- 无人值守场景（定时任务）撞上风控只能 fail-closed：状态**不**标记完成，下一轮仍接着同一集。

### 13.6 标签框与「标签 ≠ 话题」

- 标签框：`input[placeholder="按回车键Enter创建标签"]`，**逐个填 + 回车**才变成标签片（`xx ×` 胶囊）。
- 平台会**预填**几个推荐标签（实测「化学 / 初中 / 学习」），所以必填项本身不会空。
- ⚠️ B站的**标签**（决定检索与分发）与**话题**（简介里的链接）是两套东西。把 `#标签` 打进简介，检索侧一个标签都没有——标签要填进标签框。

### 13.7 ⚠️ 一个 user-data-dir 里有多个账号时，必须钉死 profile

实测 `~/.bili_creator_profile` 里有 `Default` + `Profile 1…9`，**每个是一个不同的 B 站账号**（Local State 的 `profile.info_cache` 里各有一份账号名）。

Chromium 不传 `--profile-directory` 时用的是 Local State 里 `profile.last_used` 记的那一个 ⇒ **别人手动开一次 Chrome 就可能把定时任务的登录态换成另一个账号**，无人值守时把片子发到错账号还不报错。

⇒ 发布器新增 `--profile-name`（透传 `--profile-directory`），日更产线固定用扫码登录时的那一个。

**验证方式**：以上每条都由 DOM 探针实测（`usine/examples/periodic-12lang/tools/probe-bili-*.mjs`，2026-11-15），探针只点表单控件、**不点存草稿/投稿** ⇒ 不落库、无平台状态残留。跨项目复用前仍要按纪律 4 重摸。

### 13.8 ⚠️⚠️ 创作声明是**两个字段**，被一条分隔线隔开（2026-11-15 逐字 dump 推翻旧结论）

`ul.bcc-select-option-list` 的直接子节点是 **9 个**，不是 7 个：

| 下标 | 节点 | 属于 |
|---|---|---|
| 0–5 | `article.option-hover-tips > li.bcc-option`（内容无需标注 / 含AI生成内容 / 含虚构演绎内容 / 内容含营销信息 / 个人观点，仅供参考 / 内容为转载） | **必填创作声明** |
| 6 | `div.option-divider` | 分隔线 |
| 7 | `div.auth-title`「是否添加内容授权声明（**非必选**）」 | 区块标题 |
| 8 | `article.option-hover-tips`「内容为自制：未经作者允许，禁止转载」（**无 li 子节点**，内部是 `div.auth-content > span.option-text`） | **非必选的内容授权声明**（另一个字段） |

**旧结论是错的**：2026-11-03 那版判定「自制与内容无需标注并列，就是必填声明的一个选项」，并把它写成必填首选。2026-11-15 按结构 dump 推翻——它被分隔线与「（非必选）」标题明确划到另一个控件，且**不接受「当作声明选项」这种点法**（点什么都没反应，`input.value` 不变，合成 click 与 `pointer-events:none` 让开提示层都无效）。

**结构性判据**（不要用文字判）：必填选项都有 `li.bcc-option` 子节点，授权声明那行没有。读选项、点选项都只在这 6 项里做；退回「扫视口读文本」会把两个字段混成一张表，正是这条歧义的来源。

> 这一条同时是个方法论案例：**「点不动」不一定是选择器过时，也可能是「把它当成了错的字段」**。差别在于——选择器过时可换写法，字段错时任何写法都不生效。

### 13.9 ⚠️⚠️ tsx 的 `keepNames` 会把 evaluate 回调改坏（跨项目通用坑）

**现象**：`page.evaluate`/`locator.evaluate` 回调里只要出现**具名函数**（最常见是 `const vis = (e) => …` 这种内层辅助函数），页面里就抛 `ReferenceError: __name is not defined`，而外层看到的只是「每个候选都点不动」——极像选择器过时。

**根因**：`tsx` 的 esbuild 变换写死 `keepNames: true`（`node_modules/.pnpm/tsx@*/node_modules/tsx/dist/index-*.mjs` 里 `keepNames:!0`，不可配置），把 `const vis = () => {}` 改写成 `const vis = __name(() => {}, "vis")`。这段源码被序列化送进浏览器执行，`__name` 是 Node 侧注入物、页面里不存在。**`feuille` 的 CLI 本身就是 `node --import tsx` 直跑 TS 源码，所以这是生产路径的系统性缺陷，不是探针特例。**

**判据**：在 Node 里打印回调的 `fn.toString()`，看到 `__name(` 就中了。一行即可复现：

```js
const f = (x) => { const g = (y) => y * 2; return g(x) }
console.log(f.toString())   // x=>{const g=__name(y=>y*2,"g");return g(x)}
```

**修法**：启动浏览器时给页面垫一个 no-op `__name`（`base.PAGE_SHIM_JS`，经 `ctx.addInitScript({ content })` 挂上）。用 `{content}` 而不是传函数——**这段就是要在页面里逐字执行**，传函数反而会被同一套变换包成 `__name(...)`，在垫片自身生效之前先炸掉。

**不要**改成「回调里不许写具名函数」：那是纪律，不是机制。含内层辅助函数的回调在发布包里至少 6 处，靠纪律守不住，而且复发时的报错指向完全无关的地方（本次指向创作声明选择器）。

### 13.10 判「点生效没有」必须轮询，不能睡死再读一次

同一轮实测里叠了第二个缺陷：固定 `sleep(1.5)` 后读 `input.value`、读到空就判「没生效」，于是循环去点下一个候选，**每个候选都真点下去了、后一个覆盖前一个**，最后落在候选表最后一项（实测落成「含AI生成内容」），脚本还以为自己在「逐个试到能点动为止」。

⇒ 一律用「轮询到不变量成立」（`waitValue(target, 6s)`，250ms 一次）。**定长睡眠是把时序假设写成代码**，UI 慢一点就变成逻辑错误。

**这两个缺陷叠加时尤其难查**：`__name` 让所有点击真的不生效，轮询缺失让偶发不生效被当成「这个候选不行」，两者都会表现成「所有选项都点不动」。修好垫片后必须重跑一遍候选选择——否则会被前一个缺陷的假象带着继续怀疑选择器。

### 13.11 ⚠️⚠️ B站封面：**必须先在帧条里选中一帧**，「完成」才会提交（2026-11-15 实测）

这是整条 B 站发布链路上最反直觉的一处，也是我在这上面白跑了七八轮探针的原因：**编辑器里没有「当前帧」时，点「完成」不提交，而且不报错**——弹窗不关、主表单不变、页面零 `pageerror`、零 toast。看上去像「这个键点得不对」，实际是它在等你选。

正确的操作顺序只有三步：

1. 点主表单封面位 `div[class*='cover-slot']`（`cover-empty-pill` 在本机**恒为 0**，别再用它）打开「封面制作」。
2. 点帧条里的一帧：`div.cover-slider-image-list div.cover-slider-image`。帧条是**片长上的等距采样点**（实测片长 40–41s 给 7 帧），所以「第 N 秒」只能落到最近的采样点上，取帧精度被平台量化。
3. 点「完成」：精确选择器是 `div.cover-editor div.button.submit`（`getByText('完成', {exact:true})` 点到的是别的节点，无效）。

判据必须看**主表单封面的指纹变化**，不能用 `<img>` 计数：

- 封面位一直是满的——视频传完后 B 站会自己取一帧当默认封面，落在 `div.cover-module-main div.cover-img` 的 `background-image` 上（base64，约 20 万字符），而这个 div 里**没有任何 `<img>`**。所以 `querySelectorAll('img').length` 恒为 0，用它判「设上了没有」会让每次运行都判失败。
- 设置成功后的指纹变成 `url("https://archive.biliimg.com/bfs/archive/…")`（长度量级 ~90），与默认的 base64 指纹（~204 810）完全不同 ⇒ 用「长度 + 前若干字符」当指纹，一眼能分辨。

**不要走「上传自定义封面」那条路**（同样实测）：

- 直灌隐藏 input（`setInputFiles` 到 `div.bcc-upload.cover-upload input[type=file]`）调用返回成功、`input.files` 变成 1、`createObjectURL` 也被调用，但组件的 change 处理器**不接**：上传区不加 `has-image`、画布不动、页面零报错。
- 走真实点击触发的 `filechooser` 也**时成时败**（同一份脚本 2 成 6 败，成功时上传区会带 `has-image` 与 `blob:` 背景图）。
- 而且即使图接住了，它也**不等于「当前帧」**，「完成」照样不提交。这条路既不稳定也不够用。

结论：封面取帧走帧条，产物就是视频第 N 秒那一帧；真要放一张设计图，目前只能人工在草稿箱里换。

**另一条可搬的教训**：连续七八轮探针都失败时，先怀疑「我对这个 UI 的心智模型错了」，而不是继续加固同一个动作。这轮真正的转折点是**读组件内部状态与页面报错**（`page.on('pageerror')` + `element.__vue__`），前六轮全在猜「注入方式不对」。

## 14. ⚠️⚠️ B站标签有配额：上限 10 个，**平台预填的会占名额**（2026-11-15 实测）

**症状**：`setBiliTags` 逐个「填 + 回车 + 回读」，最后报 `标签没出现在标签区：['词源']` ⇒ fail-closed 整条中止。同一个标签在前一集贴得好好的，所以第一反应会怀疑标签内容或选择器——都不是。

**真相**（读图 + DOM 探针 `usine/examples/periodic-12lang/tools/probe-bili-tags.mjs`）：

- 标签总数上限是 **10 个**，页面自带计数器 `p.tag-last-wrp`「还可以添加N个标签」；
- 到上限后平台弹 toast「允许添加的标签已经达到上限了」（截图里带颜文字），多出来的那一个**静默不落**——脚本侧只看到「回读缺一个」；
- 平台**预填 3 个推荐标签**，且预填内容**会漂**：同一账号同一天实测到「化学 / 初中 / 学习」→「影视剪辑 / 原创 / 剪辑」→「生活记录 / 旅游 / 记录」→「学习 / 地理」→「历史 / 影视剪辑 / 原创」；
- 我们清单 8 个 + 预填 3 个 = 11 > 10 ⇒ **清单末位那个被平台拒掉**。

**DOM（逐字 dump）**：

```
div#tag-container.tag-container
  div.tag-input-wrp > div.input-container
    div.tag-pre-wrp > div.label-item-v2-container
                         p.label-item-v2-content   ← 标签文字
                         svg.close                 ← 删除「×」
    div.input-instance > input[placeholder='按回车键Enter创建标签']
    p.tag-last-wrp                                ← 「还可以添加N个标签」
```

**处置口径**（`packages/publish/src/bilibili.ts` 的 `setBiliTags` + `pruneForeignTags`）：

1. **填之前先清掉「不在清单里」的预填胶囊**。预填的是平台猜的，不是作者写的；按 `data/publish-copy/*.json` 的标签集发，不让平台猜测挤掉它。
2. **清理必须每轮重查 DOM**，不要先 `count()` 再按下标遍历：点掉一个胶囊后 DOM 重排，旧下标会漏掉紧邻的那个（实测预填 3 个只清掉 2 个，「原创」被跳过）。轮数上限给 12（上限就是 10 个胶囊）。
3. **删不掉就停手，但绝不静默**：回读缺哪个就报哪个，并把配额计数器一起打进日志——只报「缺 词源」会把排查引到标签内容上。

**判据**：`我加了 N 个` 不是判据；`已有 + 要加的 ≤ 平台上限` 才是。任何「往表单里加东西」的自动化都要先读已占用，再算余量。

## 15. ⚠️⚠️ B站草稿箱上限 30 个 = 批量备稿的**停机线**（2026-11-15 实测）

草稿箱上限这件事**早就写在页面 tips 里**（「草稿箱最多保存30个稿件」，见 §12.2），但一直只当注脚；真跑到批量备稿时它是**硬停机线**。

**撞上时的现场**（第 31 条，此前 30 条全部成功）：

1. 点「存草稿」后**没有落库信号**（URL 没跳 `upload-manager`）；
2. 发布器按既有逻辑「再点一次草稿键」重试；
3. 第二次点击被弹层拦住 ⇒ `locator.click: Timeout 10000ms exceeded`，拦截者原文是 `div.dialog.bcc-dialog__wrap-mask`（来自 `div.max-draft-count` 子树）；
4. 弹窗逐字：标题「**保存失败**」、正文「**草稿箱已达到上限（30个），暂不支持继续添加**」、按钮「我知道了 / 去管理」。

**症状极具误导性**：日志第一行是「点击后没检测到落库信号 → 再点一次草稿键」，看着像时序或选择器问题。**判据：重试点击被 `max-draft-count` 对话框拦住 ⇒ 是配额，不是时序。** 读到这个 `div` 就该停，不要继续加固点击逻辑。

**停机口径**：

- 批量开跑前先算：`待备集数` vs `30 − 现有草稿数`。不够就**别开跑**，先把差额报给用户。
- 跑中撞上就**停**：不自动重试、**不删草稿腾位**、更不点投稿。删草稿等于毁掉已备内容，点投稿是不可撤回的对外动作——两者都只能由用户决定（与「跳过」不同，这是没有安全默认值的一步）。
- 失败的那一集**不标记 done**，配额一放开就从同一集续跑（与风控 fail-closed 同一条状态语义）。

**批量驱动落位**（脚本一次只备一集时）：

- 外层串行循环，**同一 user-data-dir 只允许一个 Chrome**，绝不并发；
- 每块给**时间预算**（bash 单命令 3600s 上限，取 3000s 收口），到点退出并报进度，下一块从状态文件续跑；
- `rc != 0` 立即 break —— 不吞错、不跳过；
- 不加 `--headless`：风控要账号本人过短信验证，必须留可见窗口（见 §13.5）。

## 16. ⚠️⚠️ B站「投稿」**不消费草稿**——草稿箱不会因为发完就自己清空（2026-11-15 实测）

这条推翻了「投出去草稿就没了」的直觉，而它在批量发布里是**结构性**的：草稿箱上限 30（§15），如果投稿不消费草稿，那么「发完 = 清空」永远不成立，下一批备稿必然继续撞上限。

**实测证据**（同一晚，两次独立确认）：

1. 投出第 1 集（氢）后，草稿箱仍是 30 条，卡片列表里那条还在；
2. 按 `draftId=4124995` 直接打开编辑页，**标题、分区、标签、简介、封面全都还在**，表单可用；
3. 再投第 2 集（锂），草稿箱仍 30 条。

⇒ **「投过了」的唯一证据在稿件管理里，不在草稿箱里。** 由此得到两条必须写进脚本的闸门：

- **跳过闸门（防重复投递）**：发布前先读稿件管理的标题集合，标题已在里面就跳过。少了这一步，重跑一次 = 同一支片子发两遍。别用「草稿还在不在」当判据——它恒为真。
- **清空必须显式删**：要空草稿箱只能删草稿。这是**不可恢复**动作，只在用户明确授权后做，并且**先发后删**——只删「标题已经出现在稿件管理里」的那些，没投过的草稿一律留着（删了就得重走一遍备稿）。

**稿件管理里的行怎么读**（列表没有稳定 class，第一版判据两次都读到 0 条）：

- **判据用「整页正文 + 标题 includes」，不要切行容器。** 实测稿件管理的行**没有稳定容器结构**：按 `section/li/tr` 匹配拿到 0 行，而 `document.body.innerText` 里有全套文案（`<标题>` 换行 `<提交时间戳>` 换行 `<状态>` 换行 `<定时时刻>` 换行 `查询进度` 换行 `编辑`）。`innerText` 每个 cell 独占一行，标题足够长（带「｜元素周期表 · 第 N 号」）不会误撞，`includes` 就是够用的判据。逐页累积整页正文，翻完再判。
- 标题清单（只作**人读证据**，不作判定依据）从行序取：时间戳行的**上一行**若不是时间戳、不是 `HH:MM:SS` 时长，就当标题。实测这份清单条数与平台自己的总量完全一致（`共11页 / 102个` ⇒ 认出 102 个标题）。
- **被推翻的旧判据**（留档别再用）：「同时含提交时间戳与『查询进度』的最深容器，标题 = 第一个时间戳之前那段」。它取到的最深容器是**右侧状态栏**，文本**以时间戳开头**，`m.index > 0` 于是把所有行都过滤掉 ⇒ 静默读到 0 个标题、闸门形同不存在、一条都不跳过（若照此发布，平台上已有的 5 条会被重投一遍）。
- **读页失败必须判死，不许当「平台上一条都没有」**：`listTitles` 认出 0 条就中止，不点投稿、不删草稿。读到 0 与「真的空」在返回结构上分不开，唯一的区分办法是页面上明明有总量（`共N页 / M个`）却认不出标题——那就是读页坏了。

**删一条草稿的实况**（`tools/probe-bili-delete.mjs` 先摸一遍再动手）：

1. 草稿卡片右下角那个 `button.bcc-cmadc-btn`（内含垃圾桶图标）就是删除键；
2. 点它弹出确认框，按钮是 `button.bili-btn.ok`（「确定」）与 `button.bili-btn.cancel`（「取消」）——**取消键存在**，先摸弹窗再删是零成本的；
3. 点「确定」后卡片从列表消失；判据要**回读同一标题还在不在**，别信点击返回值。
4. **`goto` 之后不许用固定 sleep 等列表**：草稿箱是异步渲染的，页面还在加载/重排时 `querySelectorAll('section.bcc-cmad-card')` 返回 0 条，那条草稿就被判成「没找到」而漏删。实测 30 条清空漏了 1 条（其余 29 条全中，而那条一直在箱里），症状是「草稿箱里没找到这条草稿（可能已被删）」——**它没被删，是没读到**。判据要「等到至少一张卡片出现再往下走」，空箱靠超时兜底、最终仍按「命中 0 条」拒绝删除，方向没变。补删重跑一次即可（脚本幂等：按标题定位，删过的自然找不到）。

**定位一条草稿不要靠点击卡片**：卡片上封面框 / 标题 / 「编辑」三处 `<a>` 的 href 都是 `/platform/upload/video/frame?type=draft&draftId=<id>` ⇒ 直接 `page.goto` 即可。点卡片要先 `scrollIntoView`，否则卡片在首屏下方时 `mouse.click` 落在视口外——**点了没反应、URL 一点没变，而报错里什么线索都没有**（2026-11-15 第一版探针就栽在这里）。

**同一天多条都设同一时刻是允许的**：实测 11-16 09:00 有两条（氢、锂）都稳定保留，平台不会把它们挪开。所以「每天 N 条、全部 09:00」是可执行的排期，不必自行错开分钟。
