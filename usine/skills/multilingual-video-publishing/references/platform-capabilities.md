# 平台能力边界与实测结论

> 只记**本skill 实跑验证过**的结论。每条都注明验证方式与日期。
> 手册（`docs/publish-playbook.md`）记的是跨项目通用流程；
> 本文记的是**多语种 + 横竖双版**这个具体形态下新测出来的东西。

## 1. 双版式分发：竖版 → 抖音，横版 → B站

《四季》项目的选型依据（2026-10-08，用户拍板）：

| 平台 | 版式 | 依据 |
|---|---|---|
| 抖音 | 竖版 720×1280 | 信息流吃竖屏；封面 3:4 与项目 1080×1440 原生一致，零裁切 |
| B站 | 横版 1280×720 | B 站是横屏观感，竖版浪费两侧 |

**不要默认「同一批素材发同一版式」。** 双版式项目分发时按平台的
主要消费形态选，封面原生比例能对齐就不要再裁。

## 2. B站合集：Lv2 门槛，**做不到就是做不到**

`src/feuille/publish/collections.py` 头注已记录：合集需创作中心 Lv2，
等级不够时编辑页是灰字、无可点控件，合集管理页 404 或重定向。
`collections.py` 里**只有抖音实现了全流程**（`fix_collection` /
`create_collection` 都是抖音 URL）。

**处置**：本批 B 站 12 条**裸投稿、不建集**，如实告诉用户合集等升级后再补挂。

> 这条的教训不是「B站没有合集」，而是：
> **能力边界要在承诺之前查清，而不是发到一半才发现。**
> 承诺了做不到的事，代价由用户承担。

## 2b. ⚠️⚠️ 抖音合集「挂不进去」的三层原因（2026-10-08 实测，逐层剥）

**现象**：`create_collection(want=12)` 报「面板无未添加行，待加=0」，
四次重搜全是空。但**截图明明白白有作品、每行右侧都有「+」按钮，完全可点**。

按手册坑 1.2 的说法，这像是「作品面板被服务端错误清空」。**但不是。**
根因是选择器里三处**硬编码实测值**：

| # | 硬编码 | 实际 | 后果 |
|---|---|---|---|
| ① | `r.x < 1500 \|\| r.x > 1600`（JS_PLUS） | viewport=1700 时「+」在 **x≈1674** | **全部候选被过滤** → 报「没有未添加的行」 |
| ② | 行文本必须 `includes(search_kw)`，传 `"四季"` | 12 条标题里**只有 3 条**含「四季」 | 9 条**静默漏挂** |
| ③ | `JS_PANEL_EMPTY` 把「没有更多视频」当故障 | 那是**分页到底**的正常文案 | 把正常状态误判为异常 |

**修法**：① 改为**相对视口**判定（`r.x + 24 < vw * 0.62` 排除 → `r.x > vw - 14` 命中）；
② 去掉文本过滤，「未添加的一律返回」，数量核对交给调用方；
③ 判据改成「共 0 个作品」或服务端错误。

**同时**把 `JS_COUNT` 从二态改成**三态**——原来空合集时页面根本没有
「合集内作品 N」这段文本（只有标题 +「点击添加作品」），
正则匹配不到返回 **-1**，与「面板被清空」混为一谈。现在：
正数 = 计数 / 0 = 确认空 / -1 = 未知。

> **教训（比修法重要）**：
> 「面板空了 → 平台故障」是一个**过早的结论**。先去看截图。
> 本项目里平台一直是好的，错的是选择器——
> 而且是那种「自己量了一次、写成常量、再也不复核」的量。
>
> 硬编码的几何量（x 坐标、尺寸、视口宽）**必然会在另一个项目失效**，
> 而且失效方式是**静默的**：不报错，只是返回空结果。
> 凡是把实测值写进选择器的地方，都要问一句「换台机器还成立吗」。

## 2c. ⚠️ 同一份几何判据写了两遍 → 修好一处漏一处

上一条修完 `JS_PLUS` 后，挂入数从 **0 → 9**（12 次点击）。但**离 12 还差 3**，
且日志显示轮 10/11/12 **加的是同一条希伯来语**，连点三次。

**根因**：`_add_loop` 里为了「滚动进视口再取新鲜坐标」**另有一段 JS**，
里面**又抄了一遍** `r.x > 1500`。两处硬编码，修了 `JS_PLUS` 却漏了这段——
滚动永远找不到元素 → 拿旧坐标 → 点到同一行。

**修法（两条都要）**：

1. 两处几何判据**统一成相对视口**的同一份写法
2. **加去重护栏**：按行首文字 `seen` 集合，已点过的直接跳过；
   连续 6 次取到同一支就判定「定位失效」并停止

**为什么第 2 条比第 1 条更重要**：第 1 条治的是这次的病因，
第 2 条治的是**这类病的家族**——任何「循环点 N 次」的批量操作，
一旦坐标或定位逻辑失效，**重复点击会伪造出一个看起来合理的计数**。
12 次点击 → 计数 9，而日志里 `added.append` 记了 12 条。

> **计数必须按「不同的东西」数，不是按「操作次数」数。**
> 批量 UI 操作里，这是最容易被自己骗过去的地方。

> 另外注意：**同一处逻辑抄两遍几乎必然漂移**。修的时候要 `grep` 全文件，
> 不是只修你看到的那一处。

## 2d. ⚠️⚠️ 封面补传「定位器写死了上一个项目的标题格式」

**现象**：`fix_covers(--only 1)` 报「页面有 3 个「编辑作品」按钮、**0 个标题**」，
整条卡在「没找到那条」。

**根因**：`douyin.fix_one` 的标题定位器写死成

```python
titles = page.get_by_text(f"「{search_kw}」的", exact=False)
```

即「**「X」的Y版**」这种标题格式——那是**上一个项目**的文案格式。
本项目标题是「老树枯枝立野原，中文的冬天很轻」，**不含该结构** → 匹配 0 个。

**与 §2b 是同一类病**：**把某个项目的文案格式/坐标当成通用格式**。

**修法**：直接用**清单里的真实标题**做前缀匹配，与文案格式解耦：

```python
rows = [(i, eds.nth(i).locator("xpath=../..").inner_text()) for i in range(eds.count())]
idx = next((i for i, t in rows if want[:10] in t), None)
```

### ⚠️ 但这个修复引入了更严重的问题（未完成，请勿照抄）

改成「全页定位退化分支」后（`all_titles.nth(j)` 与 `eds.nth(j)` **按下标对齐**），
第 1 次验证把**中文的封面盖到了韩语的作品上**——编辑页截图里标题是
「가을이 깊이 오니」，而脚本自报 `✅ [01] 中文`。

**根因**：两条作品在页面上的**下标不一致**（标题元素与编辑按钮属于不同容器树，
各自 `nth()` 的枚举顺序不能保证对应）。「同一下标」是个**看起来无害的假设**。

> **教训（下一次从这里接着做）**：
> **批量 UI 操作里，「元素 A 的第 i 个 == 元素 B 的第 i 个」是默认假设，
> 而这个假设通常不成立。** 必须用**可观测的关联**（共同祖先容器、
> `data-*` 属性、同一行的文本），而不是靠下标对齐。
>
> 另一个更硬的规矩：**补封面 / 改文案这类「修改已有作品」的操作，
> 在编辑页必须回读标题并与清单逐字比对，不一致就中止**——
> 改错对象比没改更糟，因为它消耗修改额度（抖音上限 5 次/作品）
> **而且看起来是成功的**。

## 2e.⚠️ 同一批作品里，旧项目与新项目可能同名冲突

面板里能看到 **2026-10-06 发布的旧作品**（时长 00:15，标注「已加入其它合集」）。
合集面板「共 60 个作品」里混着历史批次。

**影响**：
- 用标题关键词搜索会**搜到旧作品**，从而加错对象；
- 已在其它合集里的作品**不能重复加入**，点击静默无效——
  脚本会以为「点过了」，实际计数不变。

**判据**：进面板后先看**发布日期**，只有本批日期的作品才是目标。
不要只看标题像不像。

## 2f. ⚠️⚠️ 核验「列表页」本身不可靠——必须用服务端过滤

**现象**：同一批稿件，两次核验分别报「缺中文+日语」和「缺中文+德语」，
但稿件时间戳是**连续**的（说明都在）。页面文本长度两次都是 11745 字。

**根因**：稿件管理页是**懒加载 + 分页**。靠滚屏读全文会漏——
读到的边界在飘，**两次漏的不是同几条**。

**更严重的后果**：漏读会被当成「没发出去」，
从而触发**重发已经发过的稿件**，产生真的重复作品。

**修法**：用**搜索框**逐条核验。搜索是**服务端过滤**，
输入标题片段只返回匹配项，不依赖客户端渲染完整：

```python
box = page.locator("input[placeholder*='搜索稿件']").first
for t in tasks:
    box.fill(norm(t["title"])[:6]); box.press("Enter")
    hit = norm(t["title"])[:6] in norm(page.inner_text("body"))
```

实测：**滚屏报 10/12，搜索报 12/12**——后者是对的。

> **教训（这条比前面所有条目都重要）**：
> **核验工具自己也会有假阴性。**
> 前面几条讲的是「怎么让核验工具别骗自己」，这一条是
> **「先确认核验工具本身可信，再去相信它的结论」**。
>
> 识别方法很简单：**同一份数据，两次跑出不同的缺失名单，
> 而数据没变——这就是工具不可信，不是数据有问题。**
> 数字对不上时，先怀疑判据。

### 2f.2 比对前必须归一化（码位归一会造成假阴性）

阿拉伯语标题 `قَحْطَلَت` 的前几个字母全是 harakat 元音符号，
抖音存储时会做**码位归一**（`قَحْطَلَ` → `قَحطَل`），
逐字 `in` 判定必然失败。

```python
def norm(s):
    return "".join(
        c for c in unicodedata.normalize("NFD", s)
        if not unicodedata.combining(c)
        and unicodedata.category(c).startswith(("L", "N"))
    ).lower()
```

实测：归一化前报「阿拉伯语未发布」，归一化后 12/12 全中。
**假阴性的危害和假阳性一样大**——都会导致重发或漏改。

## 3. 封面在抖音是「发布后补」，不是「发布时设」

`douyin.publish_one` 走的是两步法：发布时**不设封面**，发布后用
`fix_covers` 走编辑流程补。原因写在脚本输出里：`upload_files` 的工具限制，
发布表单的封面面板喂不准。

手册 §0 的能力边界（坑㉗）也记了同一件事：自定义封面**传不上去**，
小红书只能截帧、抖音是工具限制。

**所以「带封面」的真实含义是**：发布后用 `fix_covers` 补上，
**并回作品管理列表确认缩略图里有文字**才算数。

⚠️ **修改额度是硬约束**：抖音每作品**最多改 5 次**，补封面算 1 次。
`fix_covers` 的 `only` 参数就是为这个设计的——**先只补 1 条验证落库**，
确认缩略图真出文字，再批量。不要在没验证的路径上一次烧 12 次额度。

## 4. 素材命名：三套体系并存，猜错必被闸门拦下

`build_manifest` 的素材存在性前置校验会在**发布前**把猜错的路径全批拦下。
这次实测踩到两个坑，都被它当场抓住：

| 坑 | 我以为的 | 实际 |
|---|---|---|
| 成片命名 | `竖版四季_ru-RU.mp4`（locale） | `竖版四季_俄语.mp4`（**中文语种名**） |
| 封面序号 | 每个版式各自从 01 开始 | **全局连续**：横版 01–12、竖版 13–24 |

**规则：`ls` 看真实命名，再写映射。** 这道闸门是盟友不是障碍——
它把「发到一半才发现文件不存在」变成「一开始就报」。

## 5. 抖音正文末尾必须留尾随空格

`#话题` 在 blur 时会被 Slate 识别成话题候选并弹联想面板，**选中无关联想词**，
导致 `fill` 的插入语义把原文重复追加。

⚠️ 已造成线上事故：第 01 支英语发出时 242 字，正确版本只有 124 字。

**解法**：正文最后一个标签后**留一个尾随空格**，话题保持纯文本。
抖音、小红书都适用。

## 6. 判据：草稿箱计数是**假判据**

小红书在**编辑过程中就自动存草稿**，发布成功后**草稿不清理**。
实测四支全部发布成功，草稿箱却单调上涨 (1)→(3)→(4)。

**照草稿箱判会把成功报成失败 → 触发重发 → 产生真的重复作品。**

唯一权威判据：**回作品管理列表核验到这条作品**。

## 7. CLI 路由表会说谎（本 skill 顺手修掉的一个真缺陷）

`feuille/cli.py` 的文档字符串曾宣称有 `cover make`、`framehash save`、
`audit run`、`metrics analyze` 等 8 个子命令，但 `COMMANDS` 路由表里
**一个都没有**——`feuille cover make` 静默返回「未知命令」。

而 `scripts/verify_cli.py` 只机检「已登记的叶子可达」，
**不机检「文档宣称 ⊆ 已登记」**，所以它一直没被抓出来。

已修：补齐 `cover`/`manifest`/`publish` 路由，并给 `verify_cli.py` 加上
反向机检。**8/8 PASS**。

> 教训：机检的方向很重要。只查「登记的能跑」查不出「宣称的是假的」——
> 这跟发布侧「草稿箱计数查不出真成功」是同一类错误：
> **验证了 A，就以为 B 也被验证了。**

# 双版式项目特有的四个坑（2026-10-08 实测）

这四条都是「一份素材两个版式发两个平台」才出现的，单版式项目碰不到。

## 8.⚠️ 文案正文被文件尾部污染（已造成线上事故）

**现象**：12 条里**最后一条**（韩语）的话题从 6 个变成 **25 个**，
正文多出整个文件尾部的汇总表格。

**根因**：文案解析器只认 `## N · 语言` 作节的起止，但文件尾部还有
`## 附：可以直接抄的标签池`（二级标题，但不是节标题）和
`## 附：24 条对应关系`。解析器一路吞到文末，把标签池里 19 个标签
当成了韩语那条的话题。

**修法**：

```
封口条件 = 任何标题行（#{1,3}）都封口，不只是同级节标题
```

**教训**：**最后一节永远是解析 bug 的高发区**——只有它后面没有下一个
同类节标题来触发封口。测解析器时**必须单独看最后一条**，
它和前 11 条的行为不一样。

## 9. ⚠️ 横竖两版文案同名，dict 互相覆盖

**现象**：两个平台拿到的都是**竖版**文案，但抖音投竖版、B 站投横版——
文案与成片对不上。

**根因**：文案里横竖两版各有 12 节、**语种名完全相同**。
按语种存 dict 时，后一版覆盖前一版。

**修法**：**键必须带版式**——`{(版式, 语种): {...}}`，
每个平台取**与成片同版式**的文案。

> 更一般的教训：**任何"多维度分组后存 dict"的结构，
> 都要先确认每一维的组合键唯一。** 只用其中一个维度当键 =静默覆盖。

## 10. ⚠️ B 站封面必须单独出 4:3，不能靠平台裁

**现象**：把 3:4（1080×1440）封面交给 B 站，它按 4:3 居中裁切后
**标题整块消失**——只剩顶部一个「中文·春」标签。

**根因**：封面文字是**底部锚定**的，4:3 裁切窗口（810px 高）落在上半部。

**实测**：模拟裁切后逐帧看，确认底部文字一块不剩。

**修法**：给 B 站**单独出一版 4:3**（1080×810），文字块改
**横向一行**排布（`季名 ── 标题`），而不是底部竖向堆叠——
4:3 只有 1080px 宽，窄版式会让长标题折 3 行挤爆高度。

`封面.py --bili` 就是这个实现（源文件归档在 `multilingual-video-poetry` skill 的
`assets/example/` 下——封面归它，本 skill 只管投递）。

> 通用判据：**投给平台的图，先按那个平台的原生比例模拟裁切一遍，
> 看文字在不在安全区内**。能零裁切就零裁切，别指望平台替你裁。

## 11. ⚠️ Edge headless 视口亏空会吃掉底部文字

**现象**：4:3 封面渲染出来**尺寸对**（1080×810）但底部标题被切掉。

**根因**：`edge_screenshot` 的窗口高度 = `canvas_h + 视口亏空`
（macOS headless Edge 实测亏空 **84px**，与 canvas_h 无关），
截图后再裁回 `canvas_h`。

HTML 里 `bottom:56px` 是相对**视口**（894px）算的，元素被压到
810px 画布**外** 84px 处，裁完正好切掉。

**修法**：底部偏移要**加上亏空量**：

```python
deficit, _ = textlayer.viewport_deficit(1440)   # 探一次，缓存
bottom_px = BOTTOM + deficit
```

3:4 那版没暴露这个问题，是因为字号大、底部留白厚，84px 仍在安全区内。
**矮画布（4:3）比高画布（3:4）更容易踩到。**
