# 窗口预算纪律：anchor 落窗尾是本 skill 最常见的结构性错误

> 本文件的数字来自 2026-11-07 实跑（`usine/examples/weekly-2026-11-07/`，5 场欧冠集锦）。方法可复用，数字每次重测。

## 1. 症状：所有窗口一起超窗

一轮实跑里，12 个窗口有 11 个报「旁白越过窗口终点」。逐条看过去，每一窗的单条旁白时长都正常（5–9 秒），问题不在文案长度，而在**窗口本身装不下**：

```
w01  live  0.00-8.10   anchor 4.20   预算 3.45s   现文案 33 字(7.39s)   超 3.94s
w02  live  9.50-20.00  anchor 17.60  预算 1.95s   现文案 30 字(7.13s)   超 5.18s
w06  live  53.60-66.00 anchor 64.40  预算 1.15s   现文案 36 字(8.06s)   超 6.91s
```

`place_voice.py` 判 FAIL 时给出的修法是「压词或拆窗，不许把落点往前挪」——**这条修法在这种情况下是错的**，因为问题根本不是词多。压词压到 1.15 秒（4 个字）也写不出「德温特回传失误，扎卡里亚森逼抢断球，约瑟夫推空门」。

## 2. 根因：anchor 写在了窗口末尾

看预算公式（`place_voice.py` 的 `plan()`）：

```
可用预算 = t1 - anchor - LEAD      （LEAD = 0.45s）
```

anchor 是「旁白要对齐的那一帧」。它是**动作起手帧**，不是「这一窗讲完的时刻」。

把 anchor 写在窗尾，等于宣告「我只剩窗尾那一小段可以说话」——于是可用预算被压缩到窗长的 5%–40%。上表里 w06 的窗长 12.4 秒、预算只有 1.15 秒，正是这个错误。

**正确的 anchor 位置**：这一窗里**动作起手**的那一帧。

- `live` 窗：动作（起脚、扑救、抢断、射门）开始的那一帧，通常在窗的前 1/3。
- `graphic` 窗：图形页上那个「结果落点」（比分动画定格的那一下），通常在窗的末尾——**这类窗 anchor 在窗尾是对的**，因为 `align: end` 让收句落在那一瞬间。
- `jump` 窗：跳切点本身（在窗首）。
- `replay` 窗：慢镜起手那一帧，比 `live` 窗再往后 0.3–0.5 秒（先让观众认出这是回放）。

判据一句话：**anchor 之后还要装得下这句话**。装不下就是 anchor 放错了位置，不是词太多。

## 3. 抓这个错误的机检：`check_budget.py`

`scripts/check_budget.py` 是**写词阶段**的预算机检，与 `place_voice.py`（渲染阶段）配对：

```
python3 scripts/check_budget.py windows.json --voice voice-report.json
```

它判三件事：

1. **装不下**（FAIL）：`估/实测时长 > 可用预算`。修法是压词或拆窗。
2. **预算被吃掉大半**（WARN）：`可用预算 < 整窗长 × 0.35`。这条专抓「anchor 落窗尾」——它不一定是 FAIL（短句可能刚好装下），但几乎一定是 anchor 放错了。
3. **预估叠音**（FAIL）：两窗的落点区间重叠。这个在 `place_voice.py` 里也会判，但那里要等音频合成完；这里只用字数估算就能提前拦。

**为什么要有这一步**：TTS 是本 skill 最贵的一步（中文一段几秒到几十秒）。落点失败在渲染阶段才发现，就意味着「压词 → 重跑 TTS → 再判」至少多两轮往返。预算机检只看窗口表和文案，**几毫秒出结果**，让压词发生在写稿阶段。

它还可以只用文案估算（没有 `--voice` 时按字数 × 0.28s 估），所以**窗口表刚写完就能先跑一遍**。

## 4. 窗口边界该怎么来：按客观切点，不按事件印象

同一轮实跑里还暴露了第二个问题：窗口是**按「事件」**切的，不是按**镜头状态**切的。抽帧后发现母版 0–8 秒画面是 3:15–3:22 的普通进攻，窗口表却写「开场第 4 分钟托里亚尼化解射门」——`see` 描述与画面对不上，`say` 就在描述一个不存在的画面。

正确做法：

1. 用 ffmpeg 场景检测拿**客观切点**：`select='gt(scene,0.12)',metadata=print`。实测阈值 0.12 在这三支母版上给出的切点与画面内容吻合（0.25 偏粗，会把进球包的三段并成一段）。
2. 每个切点之间是一段，**一段 = 一个镜头状态 = 一个窗口**。
3. 每段抽 3 帧拼版（`tools/seg_sheet.py`），人眼读一遍：这一段在讲什么、动作起手在第几帧、有没有跳切（比分牌时钟跳变）。
4. `see` 只写**抽帧看得到的东西**。做不到就标 `visible: unread`，降级写进程轴。

跳切的判据是**比分牌时钟的跳变**，不是画面：同一支母版里 39.6→42.00 然后跳到 47:08，中间的 5 分钟没有镜头——被跳掉的时间里的事件（换人、牌）只能记 `kind: 'jump'` / `visible: 'absent'`，`see` 只写读数。

## 5. 一窗该写多少字

实测（zh-CN-YunjianNeural，rate -5%）：**0.238 s/字**（12 段实测中位数，区间 0.22–0.25）。

但真正的约束是窗长：

| 窗型 | 窗长 | 可用预算 | 拍数 | 字数上限（0.24s/字） |
|---|---|---|---|---|
| `live` | 8–13s | 窗长 − 0.45 − (动作起手偏移) | 3 拍 | 25–40 字 |
| `replay` | 3–6s | 同上 | 2 拍 | 12–22 字 |
| `graphic` | 1–2s | 极小 | 1 拍 | 4–8 字 |
| `jump` | 2–4s | 小 | 1–2 拍 | 6–12 字 |

**短窗必须压到一拍**。2 秒的图形页塞三拍就是「太满 / 太吵」（`visual-commentary.md` §7 翻车表）。

## 6. 作业序（把机检插进流程）

```
① 场景检测拿切点 → ② 抽帧读画面 → ③ 写窗口表（含 anchor / see / say）
   → ④ check_windows.py（判据 1/2/3：动作可指认 / 回放不推进 / 跳切不编画面）
   → ⑤ check_budget.py（预算 + 叠音预估）  ← 新增，在 TTS 之前
   → ⑥ TTS → ⑦ place_voice.py plan（真实时长复判）→ ⑧ 装配
```

第 ⑤ 步是本文件的全部内容：**把「装不下」从渲染阶段提前到写稿阶段**。
