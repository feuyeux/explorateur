# 成批产线纪律（多支成片时）

单支片的流程跑通了，**不代表跑第二支、第三支也成立**——批量会引入单支没有的
问题：共享的中间产物名、组内串行、批与批之间的时间边界。以下每一条都在
2026-11-14 的 236 支产线（118 元素 × 2 画幅 = 236 支，8 路并发，全程 ~2.5h）
上踩过，**每条都给出可判据的证据**。

## 1. 验收门要覆盖「产物里某个要素在不在」，而不只是「产物对不对」

验收门集合容易只覆盖**质量维度**（画面对不对、音画同步吗、时序对吗），漏掉
**存在维度**（要的东西到底在不在）。漏掉的那一维在缺失时**不报错**，而是走
降级分支 ⇒ 全部门通过，产物却是残的。

实测：`bgm` 块缺失时，`build_video.ts` 走**无床分支**照样出一支没音乐的片子，
退出码 0、不报错——而当时已有的四道门（结构 / 白页 / 出画 / 音画同步）**没有
一道能发现这件事**，因为它们看的是画面与旁白，不是「有没有音乐」。

**判据：对每道门问一句「它缺了会怎样」。** 答案是「跳过这条判据」，它就是
fail-open，必须改成**缺输入直接判死**。

### 底床门的设计（本轮新增的第五门）

- **量法**：片头卡（intro 2.5s）里 **1.85–2.40s** 只有床（fade_in 1.5s 已结束、
  旁白还没起），用 `ffmpeg -ss 1.85 -t 0.55 -af volumedetect` 量这一窗的平均电平；
- **期望值从事实源反推**，不抄常数：`床边车 measured.rms_dbfs + 20log10(gain)`，
  容差 **±7 dB**；
- **判别力必须实测**：造一个负例（故意去掉 `bgm` 块），量它与正例差多少 dB。
  实测带床 **−43.9 dBFS** vs 去床 **−91.0 dBFS**，**差 50 dB** ⇒ 容差 7 dB
  足够区分，又不会被无声蒙过；
- **无边的降级分支要显式判死**：配置里没有 `bgm` 块 ⇒ 直接判 FAIL，而不是
  「没配置就跳过检查」；
- **全量复核**：236 支实测片头窗 **−49.5 ~ −43.0 dBFS**，与反推值偏差
  **0.3–4.9 dB**，零支超容差 ⇒ 同时证明「没有一支用了旧音轨」。

复测脚本要**不依赖帧目录**（帧清了也能重测）：`measure-bed.mjs` 量全部成片的
片头窗电平，出统计到 `log/bed-levels.json`。

## 2. 清理「验收依赖的中间产物」必须放在全部验收之后

验收环节若读的是中间产物（帧目录、探针时刻表、临时波形），而同一批验收里把它
删掉 ⇒ **先跑的那批会把它删光，后跑的同组用例必然假红**。红的不是产物坏了，
是依赖被自己删了。

实测：验收脚本里「验完即删帧目录」，结果 g01 整组 14 支全红，而同脚本对
g02–g18 全绿——差异只在 g01 的帧目录**碰巧先被跑过了**。

修法：

1. 验收阶段**一律不清帧**（除非显式开关）；
2. 清理**独立成一步、放在最后**；
3. 清理脚本自己按配置取路径（`formats[].frames` 字段），**别用通配符**——
   组目录下还有 cover/out/tts 等非目标产物；
4. 清理脚本先 `--dry` 列清单，核对数量与体积再真删。

## 3. 固定名中间产物被两个进程共用时，报错的是受害者

目录里有固定名中间产物（`video_noaudio.mp4`、`audio_all.wav`、`concat_*.txt`）
时，两个进程同时跑同一目标，症状几乎不会是「冲突」——而是其中一方报「**我要读
的文件不存在**」，因为另一方**收尾时把共用的中间文件 unlink 掉了**。于是你会
去查那个报错的进程，而它其实完全无辜。

**判据（比读代码快）**：把该目录下中间产物的 mtime 按时间排一行。出现
「A 的产物 / B 的产物 / A 的下一件」这种**交错**，就是两个进程在同一个目录里
写字——单进程只能是严格串行的时间序。

实测识破点：`_bgm_track.wav` 的 mtime 夹在 `_vseg025`/`_vseg026` 之间——
单进程不可能在「编码分段」的中途去写 BGM 轨。

配套：**同组只能有一支在构建**（固定名中间产物是组目录级的），组间可并发；
要冒烟就**先停队列**，或用队列里没有的组。

## 4. 改底床/场景后要整批重渲，别让驱动器按「产物已存在」跳过

改了底床或场景，成片还是旧版本——因为驱动器按「产物已存在」跳过。需要一个
显式的**强制重排**开关（`-Force`）：成片已存在也重排，ffmpeg 用 `-y` 原地
覆盖。「删掉旧成片再渲」也行，但多一次删除，且后续迭代不能复用。

配套：给驱动器加**按组过滤**（`-OnlyGroup g02,g13`）——「某组要单独重渲」是
真实需求（帧目录丢了要拿回来、只想迭代一组的底床），不该每次都手写脚本。

## 5. 状态文件要能扛住残缺

验收脚本读写的状态文件（构建报告之类）可能是残缺的：手工清空成 `{}`、旧批次
遗留别的结构、写到一半被中断。此时 `report.jobs[name] = …` 会抛
`TypeError: Cannot set properties of undefined`，整批**刚跑一支就崩**。

修法：解析后统一补 `jobs` / `started` 兜底，坏 JSON 也要兜底。

## 6. 别让两处写同一个日志文件

- `Start-Process -RedirectStandardOutput X` 与命令内部的 `Tee-Object -FilePath X`
  会互相锁死（"cannot access the file ... because it is being used by another
  process"），输出全丢。**选一种写。**
- 验收脚本**别把 stdout 写到逐门详细日志的同一路径**——那会把底床实测电平、
  白页扫描输出这些**逐门实测值覆盖成一行摘要**，事后不可恢复。stdout 另存
  `.stdout.log`。

## 7. 渲染队列跑着时，不要并行跑验收

`verify-sync` / `check-edges` 要读帧目录，正在构建的组帧目录不完整 ⇒ **假红**。
要么等队列跑完，要么只验已完成的组。

## 8. PowerShell：别把子进程的输出接进 `Select-Object -First N`

`-First N` 会在取到 N 行后**关闭上游管道** ⇒ 在跑的子进程收到 broken pipe 被杀
⇒ 表现是「链失败且**没有任何输出**」，像脚本本身炸了。

要限量就**先把输出落文件再读文件**；`-Last N` 是缓冲到末尾才输出，可以安全用。

## 9. 遗留的旧结论要清掉

旧批次的验收结论文件会**堆在同一个 log 目录里**，与新批次的命名不同（如
`verify-g01-landscape.json` 缺 z，而新的是 `verify-g01-1-landscape.json`）。
它们不会影响按 gid-z-fmt 精确读的汇总脚本，但**留在那里会误导人**——结论还是
旧的、门还少一道。

收口时按「当前配置算出的期望文件名集合」与磁盘上的实际文件名求差，把差集删掉
（走回收站）。别用通配符删 log 目录——同目录还有本次的详细日志与原始输出。

## 一句话版本

**批量产线的坑几乎都不在「做对一件事」上，而在「做很多件事」上**：共享的
中间产物名、门的盲区、清理的时机、日志的落点。每一条的判据都是可查的
（mtime 交错 / dB 差 / 退出码 / 文件名差集），不要靠感觉。
