四、L2 入口与装配：六个组件

这一层只做两件事：把宿主起起来、把插件装上去。任何产线逻辑都不在这层。

ask.mjs宿主对话框

三挡入口共用一个 makeHarness()：preflight（零 LLM 四道检查）、ask（交互，逐行 readline）、ask 自检（单发一句即退）。

ask.cordis.yml本入口的 overlay

叠在 dsh sdk 剖面上、不动 ~/.dsh：① 补 provider 条目 ② insert 插件 ③ approval policy。

给 dsh 自家宿主用（如 npx @deepseek-ai/dsh web）：只插插件，不带 provider 与 approval 配置。

credentials.mjs凭据解析

八、一次调用在 dsh 里怎么走

关键在 alt / else 那一支：红线在派发层就分叉了。被拒的那条路径里，工具体从头到尾没有执行——不是执行完才告诉你不行。

门返回 ask 后由 dsh-tools 的 serviceAsk 接审批：无 approval 服务 → deny；无 agent → deny；四种结局 allowed-once / rejected / cancelled / unavailable 各自映射成可区分的拒绝理由。pre-execute 之后还有一道单调 guard——任何 guard 可以否决，但没有 guard 能强行放行另一个 guard 已否决的调用。

九、四个必须记住的 dsh 行为

这四条都是「读源码读出来的、文档里没直说」的机制——踩过的坑都在这。

01inject 是 AND 语义，不是「可选声明」

fiber 的 _refresh() 遍历 inject，任一服务拿不到就置 epoch=INACTIVE——fiber 永不生效，插件整体不挂载。

症状
工具面全空，宿主毫无报错
本项目
inject = ['tools']（只留真硬依赖）
实测
缺 systemPrompt：0 → 17 个工具

02ctx.inject 等服务，ctx.get 直接读

ctx.inject(deps, cb) 是子 fiber：等 deps 到齐才跑 cb，等不到就静默不跑；ctx.get(name) 读当前可用服务，读不到返回 undefined。

approval
上游 ctx.get（无服务即降级 deny）
skills
ctx.inject(['skills'], …)
systemPrompt
ctx.inject(['systemPrompt'], …)

03审批是「派发层」的事，不是工具的事

工具自己问审批 = 工具已经执行过。宿主唯一能按工具名否决的接缝就是 pre-execute；审计事件也只在派发层产生。

结局
allowed-once / rejected / cancelled / unavailable
审计
approval/asked + approval/decided（log-only）
本项目
门只门视频 submit；不合规的放行给工具体回 invalid

04返回值由 dsh 按 schema 机检

output.schema 在运行时强制执行（additionalProperties / enum / required）。契约写在代码里就是可执行的——模型看得见、门禁拦得住、跑不偏。

契约
{ok, status, output, detail}
status
ok / invalid / failed（= CLI 退出码 0 / 2 / 1）
render
把结构化值摊平成模型可读文本
